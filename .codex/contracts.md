# Interface Contracts

`simulate` input contains profiles (`mechanics`, `unit_stats`, `economy`, `workshop`, `forge`, `support`, `targeting`, `battle_end`, `formation`), policy, an explicit battlefield ID (`land-mini`, `land-small`, `land-medium`, `land-large`, or `land-max`), max rounds, and armies with side `forge_level` plus `units[{unit_id,quantity,wave_id,attack_upgrade,armor_upgrade}]`. Town Hall ranges are descriptive metadata and do not select or resize a battlefield. `naval-mini` remains reserved. Upgrades are non-negative integers; same unit on one side must use consistent upgrades. Strict unsupported behavior is inconclusive; experimental assumptions have stable, unique IDs and only report applied policies. Snapshots keep `total` and add `main_line_holding_total`, `fallback_candidate_total`, and `continuation_state`; termination is a separate event and never fabricates casualties. `fallback_required` is an inconclusive boundary in both policies.

`GET /api/simulate` returns the canonical `Profiles()` bundle (including `formation`), verified-through metadata, all five supported land battlefield IDs and descriptive Town Hall display names, complete **player** units with domain/role/support effect plus semantic class/native line **and unit size**, Forge levels and support capacity. The same response also returns `barbarian_profile_metadata` and `barbarian_units` as a separate read-only NPC catalog. Barbarian catalog rows are never members of the player `units` collection, expose `domain = "barbarian"`, `selectable_by_player = false`, and `simulation_ready = false`, and may include catalog-only fields such as appearance levels, equivalent player unit, HP, armour, damage, accuracy, ammunition, size, and provenance. These fields document known/derived Barbarian data only; they do not make Barbarian units valid `POST /api/simulate` army `unit_id` values and do not imply that Barbarian NPC formation, targeting, morale, wall, retaliation, Workshop, or other battle mechanics are implemented. Both HTTP adapters obtain battlefield metadata from the geometry module, including each line's physical slot order and slot-space capacity; the browser selector and renderer consume that canonical geometry without a duplicate slot-count registry. `POST` returns result or 400 validation error. Packaged data is the registry authority. `attacking_matrix` additively exposes `weapon_id`; `damage_calculation` exposes `weapon_id` and `weapon_trigger` from the explicitly selected weapon.

Wave identity is entry-batch identity. Ammo live pool and frozen normal entry capacity belong to the wave and are shared by all of its slots; the percentage is Phase-A-derived rather than a verified game tooltip formula. Snapshot `waves` and additive slot fields expose entry batch, display/taxonomy, upgrades, engine-derived slot-level surviving-unit HP percentage, and wave-level munition percentage. `Wave.slots` can structurally represent more than one runtime line, but `UNKNOWN-MULTILINE-WAVE-COMBAT-SEMANTICS` prevents that uncalibrated state from entering rebuild, RR, targeting, or fire. A wholly reserve-only combat wave that formation rules make eligible for an occupied runtime line is guarded by `UNKNOWN-CROSS-WAVE-FORMATION-REBUILD`; eligibility includes native and fallback placement, while ordinary reserve refill within one wave remains supported. Heavy/Light runtime-first formation is representable. A homogeneous, single-weapon Light runtime-first wave is executable: weapon selection uses its sole weapon while targeting uses runtime first-line priority. `UNKNOWN-FALLBACK-LIGHT-INFANTRY-COMBAT` is limited to non-native Light without a uniquely selectable weapon; `UNKNOWN-MIXED-UNIT-AM-ROWS` still blocks mixed source rows. Native ranged combat selects primary and retains the existing wave ammo/partial-volley/exhaustion behavior; ranged fallback and secondary triggers remain unsupported.

`BattleReportFixture` remains backward compatible and optionally carries `fixture_id`, `evidence_class`, and `source_note`. `evaluate_fixture(fixture, simulation_result)` and `run_fixture(fixture)` return `CalibrationResult`; `as_dict()` is JSON-serializable and includes simulation status, reached round, blockers, and ordered per-field assessments. Assessments are `match`, `mismatch`, or first-class `not_assessable`. Damage percent compares persistent integer damage with the documented round-up interval over surviving slot HP. Casualties use only same-round `damage` events addressed by `target_side`, `target_line`, and `target_damage_position`; those event fields are additive observability. Battle-report life percent is retained but returns `UNKNOWN-BATTLE-REPORT-LIFE-PERCENT-SEMANTICS`. Missing/ambiguous rounds or slots never fall back to another identity.


Browser battle-workbench contract: setup rows are metadata-driven and expose quantity plus per-unit Workshop attack/armor levels; Forge/Hephaistos remains side-wide. Browser defaults select `land-max` and Forge level 5 on both sides. The initial Hoplite quantity is derived from the selected default battlefield's first-line geometry and fills that line; this is a UI starting value only and does not alter Scenario or formation semantics. The ±slot helper is a setup aid, not a combat outcome: it derives one nominal increment as `floor(selected battlefield line.slot_space / unit.size)`, preferring the unit native line and using the existing Light Infantry first-line fallback only when that native line is absent. Manual quantities remain valid and need not be slot multiples. Entry-batch/wave identity remains available under advanced controls, and the same unit type may have multiple explicit batch rows; non-zero same-unit rows must have distinct `wave_id` values so their ammunition pools cannot be normalized together, while Workshop levels must agree for that unit type on the same side. Report views separate round replay from total casualty summary and render defender/attacker lines from canonical battlefield geometry rather than hard-coded slot counts. Land report presentation follows the in-game battle-board layout: the front row is left Flank | central First/Main line | right Flank, the Second/long-range line is centered behind it, and the rear row is Air defense (`anti-balloon`) | central Third/artillery line | Air bomber (`balloon`). The attacker renders rear → second → front toward the clash line, while the defender renders front → second → rear away from it. Flank physical positions are split into left/right visual groups only for rendering; this is presentation only and physical/damage positions remain engine-owned. If the selected battlefield has no flank geometry, the browser may show a no-flank reserve note for flank-native units; it must not fabricate flank slots. Player-mode reports must always expose unsupported-mechanic IDs, evidence warnings, experimental assumptions actually reached, ordinary reserve, and `deployed_support` as a separate support section. Research mode additionally exposes per-side `continuation_state`, raw waves/batches, and events; it must not hide the player safety boundaries.

Military-score reporting is executable for current player land units through `military-economy-current`. Each unit stores an unmodified resource score-basis total and a published General Score value; profile loading requires `general_score == resource_cost_basis_total / 50`. Workshop upgrades, Forge/Hephaistos and combat buffs never change that value. Simulation output adds per-side `resource_cost_basis_lost`, `general_score_lost`, and `general_score_destroyed`; destroyed score is exactly the opposing side's loss. `combat_statistics.gross_damage_dealt` is a separate sum of emitted damage-event amounts and must not be described as military score. GET metadata exposes the land-unit score basis and General Score plus economy provenance. Barbarian resource-cost basis remains contractually zero when Barbarian profiles are implemented.
