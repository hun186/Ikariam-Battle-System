# Interface Contracts

`simulate` input contains profiles (`mechanics`, `unit_stats`, `economy`, `workshop`, `forge`, `support`, `targeting`, `battle_end`, `formation`), policy, an explicit battlefield ID, max rounds, and per-side armies with `army_kind = player|barbarian`, side `forge_level`, plus `units[{unit_id,quantity,wave_id,attack_upgrade,armor_upgrade}]`. Battlefield ID is the executable domain authority: the five `land-*` ids are supported and `naval-mini` remains reserved/unsupported. Town Hall ranges are descriptive metadata and do not select or resize a battlefield. `max_rounds` defaults to 100 and accepts 1..1000; 1000 is an explicit safety cap rather than a required battle length. Ordinary battle termination, unsupported-mechanic boundaries, and no-action termination still stop earlier. Player upgrades are non-negative integers and same-unit waves on one side must agree. Barbarian armies are a separate land-only package: Forge 0, Workshop 0, one immediate entry batch, one wave per unit type, and no mixing with player unit IDs on the same side.

`GET /api/simulate` returns the canonical `Profiles()` bundle, verified-through metadata, battlefield metadata including `domain`, all five supported land battlefield IDs plus a reserved unsupported naval row, complete player units, Forge/support metadata, and a separate `barbarian_profile_metadata` / `barbarian_units` package. Barbarian rows remain outside the player `units` collection and expose `domain = "land"`, `army_kind = "barbarian"`, `selectable_by_player = false`, `selectable_in_simulator = true`, and `simulation_ready = true` when numeric fields are complete. `POST /api/simulate` accepts Player-vs-Barbarian and Barbarian-vs-Barbarian land battles, but rejects a unit ID from the wrong army package. Barbarian resource-cost basis and General Score are both 0. Exact village-level garrison generation, walls, morale/retaliation, and naval battlefield geometry remain outside the executable contract. Both HTTP adapters obtain battlefield metadata from the geometry module; the browser consumes that canonical geometry rather than maintaining duplicate slot counts. `POST` returns result or 400 validation error; valid JSON whose top level is not an object is rejected as HTTP 400 before report options are inspected. HTTP transport is bounded independently from the pure engine result: omitting `report` (or using `report.mode = summary`) returns the complete top-level battle summary, initial/final states, casualties/statistics, assumptions/warnings, and only safety/termination-class events, with `rounds = []`. `report.mode = round_page` deterministically re-runs the same scenario and returns only rounds/events in the requested inclusive window beginning at `report.round_start`; `report.round_limit` defaults to 10 and is capped at 20. Each response exposes `report` metadata including available/returned counts and previous/next-page flags. The pure `ikariam_battle.simulate()` contract remains the full in-memory result and is not paginated. Packaged data is the registry authority. `attacking_matrix` additively exposes `weapon_id`; `damage_calculation` exposes `weapon_id` and `weapon_trigger` from the explicitly selected weapon.

Arrival-batch identity and unit-state identity are separate. `entry_batch_id` groups every unit type that reaches the battle together and carries one `arrival_round`; `wave_id` identifies one unit type's state inside that arrival batch. One `(unit_id, wave_id)` may not be reused across different entry batches because formation/state maps key that identity; such ambiguous input is rejected. Duplicate rows inside the same batch/state identity may aggregate. Legacy API rows that provide only `wave_id` remain backward compatible by treating it as both identities. Missing identity fields use legacy/default inference, but explicitly supplied `wave_id` or `entry_batch_id` values must be non-empty strings; malformed explicit values are rejected rather than defaulted. Ammo live pool and frozen normal entry capacity belong to the unit-state wave and are shared by all of its slots; the percentage is Phase-A-derived rather than a verified game tooltip formula. Snapshot `waves` and additive slot fields expose entry batch, display/taxonomy, upgrades, engine-derived slot-level surviving-unit HP percentage, and wave-level munition percentage. `Wave.slots` can structurally represent more than one runtime line, but `UNKNOWN-MULTILINE-WAVE-COMBAT-SEMANTICS` prevents that uncalibrated state from entering rebuild, RR, targeting, or fire. A wholly reserve-only combat wave is not a preflight blocker merely because it could someday enter an occupied runtime line. Same-wave center-first refill/repack runs first; `UNKNOWN-CROSS-WAVE-FORMATION-REBUILD` is emitted only when a real physical slot is currently empty and an active reserve-only wave is eligible to occupy it. This requirement is checked both after round-start refill/repack and again immediately after combat casualties, before continuation or battle-termination evaluation, because combat itself may create the first vacancy. The post-combat check first projects the supported center-first refill of every wave into its own already-owned slots; a wave with empty owned slots and its own Reserve is therefore never mislabeled as a cross-wave candidate. Only vacancies remaining after that same-wave projection may require a different reserve-only wave. This defers the evidence boundary until cross-wave placement is actually required. Scheduled entry batches activate on their configured `arrival_round` as reserve/unit-state waves; if their arrival immediately requires an unimplemented placement into an open slot, the same deferred boundary is used. That arrival/boundary round is still recorded in `rounds_completed` and appended to `rounds` as a zero-casualty snapshot so round-page transport and Debug JSON can retrieve the arrival and boundary events for the exact round. Before an engagement has started, a side with no Round-0 battle-sustaining force is not declared defeated while it still has a future combat arrival whose native line is a main-line or configured fallback candidate. The simulator records `waiting_for_arrival` and advances to the scheduled arrival. If both sides are empty at Round 0 but both have future sustaining arrivals, the Round-0 event is combined with `side=null`, `pending_sides`, per-side `pending` details, and the earliest `next_arrival_round`. Non-sustaining future artillery/air/support does not postpone a Round-0 loss. Once both sides have reached a sustaining engagement, ordinary round-boundary termination remains authoritative and later reinforcements do not retroactively keep that battle alive. Future Doctor/Cook arrivals apply the same named Experimental no-healing/no-morale assumptions at arrival time as Round-0 support, so ignored support effects are never silent. Support-assumption reach is recorded by side and round via `assumption_applied` events; a support batch scheduled beyond the simulated/reached rounds remains `not_reached`, and healing statistics become unknown only from the round that side actually reaches the healing assumption. `entry_batch_arrived.details.units` aggregates quantities by `unit_id` across all state waves in the same arrival batch so diagnostics/debug export report the full arriving force. Heavy/Light runtime-first formation is representable. A single-weapon Light runtime-first wave is executable: weapon selection uses its sole weapon while targeting uses runtime first-line priority. Mixed source unit types in one runtime formation are also executable through one shared row-major Attacking Matrix. Every source wave retains its own weapon, Workshop state and ammunition pool; each shot carries its concrete source damage-position column, and the target formation's Am address book is frozen across all source waves for that firing phase so a later source unit cannot renumber surviving target slots. `UNKNOWN-FALLBACK-LIGHT-INFANTRY-COMBAT` is limited to non-native Light without a uniquely selectable weapon. Native ranged combat selects primary and retains the existing wave ammo/partial-volley/exhaustion behavior; ranged fallback and secondary triggers remain unsupported.

`BattleReportFixture` remains backward compatible and optionally carries `fixture_id`, `evidence_class`, and `source_note`. Calibration evaluation resolves slot HP through the same combined player + Barbarian combat registry used by simulation, so supported Barbarian scenarios remain assessable for `damage_percent`. `evaluate_fixture(fixture, simulation_result)` and `run_fixture(fixture)` return `CalibrationResult`; `as_dict()` is JSON-serializable and includes simulation status, reached round, blockers, and ordered per-field assessments. Assessments are `match`, `mismatch`, or first-class `not_assessable`. Damage percent compares persistent integer damage with the documented round-up interval over surviving slot HP. Casualties use only same-round `damage` events addressed by `target_side`, `target_line`, and `target_damage_position`; those event fields are additive observability. Battle-report life percent is retained but returns `UNKNOWN-BATTLE-REPORT-LIFE-PERCENT-SEMANTICS`. Missing/ambiguous rounds or slots never fall back to another identity.


Browser knowledge/navigation contract: `戰鬥機制` and `Battle System PDF` are always-available top-level tabs independent of whether a simulation has run. Mechanics status is the user-facing accuracy/limitation register: known executable contracts, partial/calibration-required areas, and unknown boundaries must remain distinguishable. The source tab credits the empirical paper as *Ikariam Battle System* (AT Barbarossa, Xanto; 2020-07-16), links the original Gameforge forum thread, exposes the repository PDF through the stable `/ikariam-battle-system.pdf` path, and warns that its scenarios/tests predate version 13 so legacy numerical values are not treated as current data.

Browser debug-export contract: setup exposes JSON downloads above and below the army editor. The downloaded setup payload must be built by the exact same `scenarioFromSetup()` path used by `runSimulation()`, and includes the selected battlefield geometry plus combat chronology for diagnosis. The round report exposes a current-round JSON download containing the submitted scenario, summary result, exact current round snapshot, only that round's events, and explicit diagnostics (`unsupported_mechanics`, warnings, assumptions, report metadata). Deployment round 0 is downloadable as `ikariam-deployment-debug.json`. Exports are local browser files and must not include API keys or other credentials.

Browser battle-workbench contract: the Max rounds control defaults to 100 while allowing an explicit safety cap up to 1000; the player-facing UI must state that Cook morale is not yet fully modeled and must not present a common ~15-Cook player configuration as a verified fixed formula. Setup rows are metadata-driven. The default remains a lightweight one-front-line setup rather than silently pre-filling a large army. Built-in setup presets are UI-only helpers: `simple` reproduces the lightweight front-line baseline, `combined` fills one unit type per executable land combat line with reserve depth plus Doctor/Cook support, and `player-vs-barbarian` exercises the separate Barbarian package; preset quantities must be derived from current battlefield geometry and unit size rather than copied slot constants. User-defined presets serialize the same setup configuration used to build a Scenario, but omit pinned profile versions and remain browser-local under versioned `localStorage`; loading must restore battle type/battlefield, policy, max rounds, per-side package, Forge, quantities, Workshop levels, and explicit entry batches. Clearing armies zeros quantities/removes extra batches while preserving the selected battlefield, package, and Forge controls. The workbench exposes a Battle type layer (Land / reserved Naval) which filters battlefield ids, while `battlefield` remains the Scenario source of truth. Each side independently selects an Army package (Player / Barbarian). Player rows expose quantity plus per-unit Workshop attack/armor levels and side-wide Forge/Hephaistos; Barbarian rows expose quantity only, hide/disable Workshop and Forge controls, use one fixed immediate batch, and display General Score 0. Browser defaults select Land / `land-max`, Player package, and Forge level 5 on both sides. The initial Hoplite quantity is derived from the selected default battlefield's first-line geometry and fills that line; this is a UI starting value only and does not alter Scenario or formation semantics. The ±slot helper is a setup aid, not a combat outcome: it derives one nominal increment as `floor(selected battlefield line.slot_space / unit.size)`, preferring the unit native line and using the existing Light Infantry first-line fallback only when that native line is absent. Manual quantities remain valid and need not be slot multiples. Entry-batch/wave identity remains available under advanced controls, and the same unit type may have multiple explicit batch rows; non-zero same-unit rows must have distinct `wave_id` values so their ammunition pools cannot be normalized together, while Workshop levels must agree for that unit type on the same side. Report views separate round replay from total casualty summary and render defender/attacker lines from canonical battlefield geometry rather than hard-coded slot counts. Land report presentation follows the in-game battle-board layout: the front row is left Flank | central First/Main line | right Flank, the Second/long-range line is centered behind it, and the rear row is Air defense (`anti-balloon`) | central Third/artillery line | Air bomber (`balloon`). The attacker renders rear → second → front toward the clash line, while the defender renders front → second → rear away from it. Flank physical positions are split into left/right visual groups only for rendering; this is presentation only and physical/damage positions remain engine-owned. If the selected battlefield has no flank geometry, the browser may show a no-flank reserve note for flank-native units; it must not fabricate flank slots. Player-mode reports must always expose unsupported-mechanic IDs, evidence warnings, experimental assumptions actually reached, ordinary reserve, and `deployed_support` as a separate support section. Research mode additionally exposes per-side `continuation_state`, raw waves/batches, and events for the currently loaded round page; it must not hide the player safety boundaries. The browser requests a summary first, then fetches/caches 10-round pages on demand so long battles do not require one giant HTTP response.

Military-score reporting is executable for current player land units through `military-economy-current`. Each player unit stores an unmodified resource score-basis total and a published General Score value; profile loading requires `general_score == resource_cost_basis_total / 50`. Workshop upgrades, Forge/Hephaistos and combat buffs never change that value. The player `military-economy-current` map remains player-only; Barbarian sides are assigned resource-cost basis 0 and General Score 0 by the battle-statistics package rule. Simulation output adds per-side `resource_cost_basis_lost`, `general_score_lost`, and `general_score_destroyed`; destroyed score is exactly the opposing side's loss. `combat_statistics.gross_damage_dealt` is a separate sum of emitted damage-event amounts and must not be described as military score.


Morale observability is additive and does not imply a morale algorithm. Every simulation result exposes `morale_status` with `modeled = false`, stable IDs `UNKNOWN-MORALE-SUPPORT` / `EXP-MORALE-NONE-001`, and per-side Cook counts. A side with no Cook reports `not_present`; strict mode with Cook reports `unsupported_boundary` only when the morale boundary is actually present in emitted unsupported events; experimental mode with Cook reports `ignored_by_named_assumption` only when `EXP-MORALE-NONE-001` is actually present in the result's applied assumptions. If another hard boundary stops the battle before the morale assumption is reached, Cook reports `not_reached`. `effect_applied` remains false in all current cases. The common practical reference of roughly 15 Cooks is explanatory only and must never be treated as a verified fixed no-morale-loss formula. The browser must surface this status in ordinary player-facing reports rather than requiring Research mode.


Combat/healing observability is additive and must not fabricate Doctor mechanics. Each pure-engine round snapshot exposes per-side `combat_statistics` with that round's `damage_dealt` and `damage_taken`, cumulative dealt/taken values, and healing fields. Damage is derived only from emitted `damage` events: event `side` is the source and `details.target_side` is the receiver. Top-level `combat_statistics` exposes `gross_damage_dealt`, `gross_damage_taken`, and `gross_healing`. With no Doctor, healing values are numeric zero; when Doctor is present while healing allocation remains unresolved, healing values are JSON null rather than a misleading zero.

Every result also exposes `healing_status` with `modeled = false`, stable IDs `UNKNOWN-HEALING-ALLOCATION` / `EXP-HEAL-NONE-001`, the derived current capacity reference of 4000 per Doctor, and `capacity_is_allocation_formula = false`. Per-side status is `not_present`, `unsupported_boundary`, `ignored_by_named_assumption`, or `not_reached`, derived from actually emitted blockers/applied assumptions in the same manner as morale status. The 4000 value is a capacity reference only; eligibility, allocation, timing, multi-support interaction, and effective caps remain unresolved. Legacy empirical evidence also reports that Doctors do not handle Steam Giants; this is calibration evidence, not sufficient to define a current complete healing algorithm. Browser round reports must show round and cumulative dealt/taken/healing, and ordinary summary reports must show total dealt/taken/healing without displaying unknown healing as zero.


Formation chronology is an executable Art-of-Warfare contract distinct from formation filling order. Land filling order metadata is Air → Air defence → Artillery → Long-range → Close-combat → Flanks, while shot sequence is Air defence (`anti-balloon`) → Air (`balloon`) → Artillery (`third`) → Flanks (`flank`) → Long-range (`second`) → Main battle line (`first`). The same formation on both sides obtains firing eligibility from the same phase-start state. Casualties from an earlier formation phase immediately affect every later phase, but never cancel the opposing side's already-snapshotted shooters in the same formation phase.

Target priority is formation-owned and data-driven. Artillery targets only Main/First → Flank and must never silently target Long-range, Artillery, or Air. Flank targets Flank → Long-range → Artillery → Main; Long-range targets Main → Flank → Long-range; Main targets Main → Long-range → Artillery → Flank; Air defence targets Air → Air defence; Air targets Artillery → Long-range → Main → Flank. Individual shots re-evaluate the highest surviving target formation, allowing later shots to transfer after a higher-priority formation is eliminated.

Experimental kill resolution is sequential rather than pooled. Firing eligibility is frozen per side at formation-phase start; individual shots resolve in Am row order and casualties apply immediately. Until the general kill-type selector is calibrated, Experimental uses `EXP-D-KILL-SEQUENTIAL-001`: target the most-damaged current unit in the addressed slot and discard overkill. P-kill, I-kill, IR-kill, PIR-kill and M-kill remain documented empirical/open mechanisms and are not silently activated. IR and SR have explicit algorithm hooks, but their selectors remain unknown; `EXP-IR-DISABLED-001` and `EXP-SR-DISABLED-001` state that their triggers currently return false. PDF RR determines wave-to-slot aggregate persistent damage; exact within-slot individual allocation remains open, so `EXP-SLOT-DAMAGE-EVEN-001` is named when non-zero aggregate damage is materialized evenly for sequential resolution.

Current land-unit metadata exposes the in-game Human/Machine classification as `unit_class`. Human: Spearman, Swordsman, Hoplite, Spartan, Slinger, Archer, Sulphur Carabineer, Doctor and Cook. Machine: Steam Giant, Battering Ram, Catapult, Mortar, Gyrocopter and Bombardier. Doctor healing eligibility uses the Human/Machine distinction conceptually, but the actual healing allocator remains unresolved and is not enabled by this metadata alone. Naval Tender eligibility is documented separately from land Human/Machine classification.


Am slot addressing is stable across one runtime formation firing phase. When that source formation first targets a target formation class, the target class's currently occupied damage-position slots are frozen as one shared address set for every source wave/unit type in that phase. Row modulo is evaluated against that frozen set while the target class survives. If an addressed slot becomes empty mid-phase, a later row—including a shot from a different source unit in the same runtime formation—still addresses that original position; it is not redirected to another surviving slot, and the engine emits `shot_addressed_empty_slot`. This does not disable Art-of-Warfare formation-class target transfer: after the entire higher-priority target formation is eliminated, later shots may select the next formation class and establish a new frozen address set there.


Round-boundary same-wave placement is center-first and precedes RR. Within a wave's already-existing runtime slots, deployed survivors plus that wave's Reserve are re-packed in ascending damage position; because the empirical physical labels encode center-first order, this moves surviving units back toward the center before persistent damage is redistributed. This rebuild never creates a slot, crosses runtime lines, or borrows units from another wave, so the existing cross-wave and multi-line guards remain intact.

Battle-report presentation state is additive and engine-derived. Every wave snapshot exposes `reserve_damage` and `reserve_hit_points_percent`; the percentage is the surviving Reserve group's aggregate HP ratio within that one entry batch, computed from `reserve * unit_hp - reserve_damage`, and never merges damage across batches. Every slot snapshot exposes current-round `casualties`; a slot that reaches zero survivors remains present with its unit identity and `hit_points_percent = 0` so the browser can render the destroyed slot rather than turning it into a never-used empty position. Slot casualties are round-local display observability, while top-level casualties remain battle totals.

The browser battle report renders occupied and destroyed slots with unit art, a vertical surviving-HP bar, and `alive (-round casualties)`. Destroyed slots retain the unit icon in a visually dimmed/grayscale state with a 0% red HP rail only for the round in which that slot records casualties. A later round omits a still-empty zero-unit slot so the physical position renders empty; normal same-wave Reserve refill renders the new live state. Reserve is rendered as icon cards. Multiple entry batches of the same unit type are aggregated only for the player-facing Reserve card using total remaining Reserve HP divided by total maximum Reserve HP; Research/tooltip detail preserves each batch's quantity, persistent damage, HP percentage, and munition percentage.

Round navigation treats deployment as a separate `初始部署` control, not a numbered round. Numbered navigation provides first/previous, at most nine round buttons centered on the current round when possible, next/last, and direct numeric round jump. Setup rows provide one global, default-collapsed `顯示兵種數值` control; when expanded, each row displays current HP plus attack/defense derived from the unit's public numerical metadata, that row's Workshop levels, and the side-wide Forge level. The browser consumes API-provided Workshop increments and Forge effects rather than hard-coding upgrade constants.


The setup workbench hides unit name/basic metadata by default behind the global `showUnitIdentity` control while keeping icons and controls visible; the separate stat preview may wrap HP/ATK/DEF and its Workshop/Forge note. Battlefield slot faces omit repeated unit names. Battlefield and Reserve detail use one body-level fixed floating tooltip, positioned from the trigger rectangle and clamped/flipped to the viewport so parent overflow cannot clip it.
