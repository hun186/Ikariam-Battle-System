# Interface Contracts

`simulate` input contains profiles (`mechanics`, `unit_stats`, `economy`, `workshop`, `forge`, `support`, `targeting`, `battle_end`, `formation`), policy, an explicit baseline battlefield ID, max rounds, optional player-defender `town_hall_level` (1..66), optional Barbarian-defender `barbarian_village_level` (1..50), defender `wall_level` (0..48; 0 = no wall), and per-side armies with `army_kind = player|barbarian`, side `forge_level`, plus `units[{unit_id,quantity,wave_id,attack_upgrade,armor_upgrade}]`. Battlefield ID is the baseline geometry/domain authority: the five `land-*` ids and five `naval-*` ids (`mini`, `small`, `medium`, `large`, `max`) are supported, with naval Help thresholds 0+/8+/15+/22+/29+ as explicit geometry metadata; neither automated Level determination nor AM damage-address provenance is supplied by the screenshots. Town Hall ranges alone are descriptive metadata, but configured settlement + garrison state may override the effective land geometry to `land-max`; later geometry changes remain guarded rather than silently resizing. `max_rounds` defaults to 100 and accepts 1..1000; 1000 is an explicit safety cap rather than a required battle length. Ordinary battle termination, unsupported-mechanic boundaries, and no-action termination still stop earlier. Player upgrades are non-negative integers and same-unit waves on one side must agree. Barbarian armies are separate domain-matched packages: Barbarian Village units execute on land and Barbarian Fleet units execute on supported naval battlefields; Forge 0, Workshop 0, one immediate entry batch, one wave per unit type, and no mixing with player unit IDs on the same side.

`GET /api/simulate` returns the canonical `Profiles()` bundle, verified-through metadata, battlefield metadata including `domain`, all five supported land battlefield IDs, all five supported naval battlefield IDs, complete player units, Forge/support metadata, and explicit Barbarian package fields: `barbarian_profile_metadata`, `barbarian_fleet_profile_metadata`, `barbarian_units`, and `barbarian_fleet_units`. Barbarian rows remain outside the player `units` collection. Village rows expose `domain = "land"`; Fleet rows expose `domain = "naval"`. Both expose `army_kind = "barbarian"`, `selectable_by_player = false`, `selectable_in_simulator = true`, and `simulation_ready = true` when numeric fields are complete. `POST /api/simulate` accepts domain-matched player and Barbarian packages. Supported land geometries allow Player-vs-Player, Player-vs-Barbarian, Barbarian-vs-Player, and Barbarian-vs-Barbarian battles; all five supported naval battlefield IDs allow the same package pairings with player naval units and/or Barbarian Fleet units. Unit IDs from the wrong army package or battlefield domain are rejected. Barbarian resource-cost basis and General Score are both 0. Exact village-level garrison force generation and morale/retaliation remain outside the executable contract. Town Wall combat is policy-split: Strict keeps active walls behind `UNKNOWN-TOWN-WALL-COMBAT`, while Experimental executes the explicitly bounded section-state subset described below. Town Wall input itself is supported: `GET /api/simulate` exposes `town_wall` metadata, `POST` accepts `wall_level`, and every result exposes `wall_status`. Infinite Horizons / v13 current defensive wall values are `HP = 1800 + 900 × level` and `Armor = 72 × level` per section (old values ×18). The arithmetic helper `successful_hits_to_breach_wall_section(level, attack_damage)` implements `ceil(HP / (attack_damage - Armor))` for positive net damage and is explicitly a successful-hit count, not a deployed-artillery count. Current wall Damage is now calibrated as the legacy three-tier wall damage table multiplied by 18: levels 1–9 use `(10 + 2×level)×18`, levels 10–19 use `(30 + 5×level)×18`, and levels 20+ use `(50 + 10×level)×18`. Current observations Lv1=216, Lv9=504, Lv18=2160, and Lv26=5580 match exactly, so each of the three damage tiers now has at least one direct current observation. Accuracy remains unresolved; the legacy 30/50/80 values are not projected into current combat without current evidence. For a player defender with `town_hall_level`, land garrison limit is `250 + 50 × (Town Hall level + Town Wall level)`. The threshold uses actual surviving/stationed unit counts, not unit Size; since v17.4.0 Doctor and Cook are excluded. If counted defenders are strictly greater than the limit at battle start, the effective field is `land-max` and the wall is suppressed, so positive `wall_level` does not itself block those open-field rounds. If a later round (or arrival before a round) crosses the threshold and requires changing battlefield geometry, execution stops at `UNKNOWN-GARRISON-BATTLEFIELD-TRANSITION` rather than remapping wave/slot/damage/ammo state without calibration. A same-geometry `land-max` exit from an initially over-limit open field may now re-activate a fresh, previously unengaged Town Wall without remapping unit slots; the transition is recorded as `garrison_state_change` and Experimental wall combat begins on the next round. `garrison_status.transition_reached` is true for either a successful no-op/state-only threshold crossing or a guarded geometry/wall transition; `transition_blocked` distinguishes the latter, so summary transport can preserve the diagnostic even when ordinary `garrison_state_change` events are filtered. Strict policy keeps a positive active wall behind `UNKNOWN-TOWN-WALL-COMBAT`. Experimental policy now integrates the wall core into firing phases: penetration-eligible Artillery targets the wall before ordinary First, concentrates successful-hit tickets on one surviving section until breach, exposes the matching defender First damage-position when breached, and suppresses the Flank phase while any wall section survives. The exact wall section order is named `EXP-WALL-FOCUS-DAMAGE-PRIORITY-001`; treating each eligible Artillery ticket as a successful wall hit is named `EXP-WALL-ARTILLERY-SUCCESSFUL-HIT-001`; Town Wall offensive fire is deliberately omitted under `EXP-WALL-OFFENSE-NONE-001` because current wall Accuracy/individual-target interaction remains unresolved. Round-start redistribution executes only when surviving-section damage divides exactly; non-divisible remainder stops at `UNKNOWN-TOWN-WALL-REDISTRIBUTION-ROUNDING`. Barbarian garrison auto-calculation is executable when `barbarian_village_level` is supplied, using the 2024 Gameforge-forum community rule `(village level + wall level + 5) × 50`; this is algebraically the player formula with village level substituted for Town Hall level. The older Barbarian guide's `≈250 + 75 × wall level` is retained as a historical approximation rather than treated as a competing exact formula. As with player towns, strictly over-limit Barbarian defense begins on `land-max`, the wall is suppressed, and a later threshold crossing that requires geometry/wall re-entry stops at `UNKNOWN-GARRISON-BATTLEFIELD-TRANSITION`. Both HTTP adapters obtain battlefield metadata from the geometry module; the browser consumes that canonical geometry rather than maintaining duplicate slot counts. `POST` returns result or 400 validation error; valid JSON whose top level is not an object is rejected as HTTP 400 before report options are inspected. HTTP transport is bounded independently from the pure engine result: omitting `report` (or using `report.mode = summary`) returns the complete top-level battle summary, initial/final states, casualties/statistics, assumptions/warnings, and only safety/termination-class events, with `rounds = []`. `report.mode = round_page` deterministically re-runs the same scenario and returns only rounds/events in the requested inclusive window beginning at `report.round_start`; `report.round_limit` defaults to 10 and is capped at 20. Each response exposes `report` metadata including available/returned counts and previous/next-page flags. The pure `ikariam_battle.simulate()` contract remains the full in-memory result and is not paginated. Packaged data is the registry authority. `attacking_matrix` additively exposes `weapon_id`; `damage_calculation` exposes `weapon_id` and `weapon_trigger` from the explicitly selected weapon.

Round-specific Town Wall state is now an additive nullable `round.wall` field on **every** pure-engine round, including Round 0 and strict/inconclusive pre-loop exits. `wall_level=0` means `round.wall = null`. A positive wall level yields `{level:int, active:bool, hit_points:int, sections:array, wall_offense_modeled:false}`: `active=false` with `sections=[]` denotes garrison-suppressed/open-field wall, while `active=true` includes one section per physical First-line position, each `{damage_position:int, physical_position:int, damage:int, remaining_hit_points:int, destroyed:bool}`. `hit_points` is the per-section maximum, not a global sum; a destroyed section has `remaining_hit_points=0`. The `sections` array is a frozen state for the corresponding round and must not reuse the final `wall_status.sections_state` from another round. The pure engine's full result contains this on every round. HTTP `report.mode=round_page` serializes it for each returned page round, whereas `report.mode=summary` still returns `rounds=[]`; summary consumers use top-level `wall_status`. `wall_offense_modeled=false` warns that the Experimental wall display does NOT yet model Town Wall retaliation. This field does not replace `round.defender.slots` or alter attacker/defender unit slot identities.

Arrival-batch identity and unit-state identity are separate. `entry_batch_id` groups every unit type that reaches the battle together and carries one `arrival_round`; `wave_id` identifies one unit type's state inside that arrival batch. One `(unit_id, wave_id)` may not be reused across different entry batches because formation/state maps key that identity; such ambiguous input is rejected. Duplicate rows inside the same batch/state identity may aggregate. Legacy API rows that provide only `wave_id` remain backward compatible by treating it as both identities. Missing identity fields use legacy/default inference, but explicitly supplied `wave_id` or `entry_batch_id` values must be non-empty strings; malformed explicit values are rejected rather than defaulted. Ammo live pool and frozen normal entry capacity belong to the unit-state wave and are shared by all of its slots; the percentage is Phase-A-derived rather than a verified game tooltip formula. Snapshot `waves` and additive slot fields expose entry batch, display/taxonomy, upgrades, engine-derived slot-level surviving-unit HP percentage, and wave-level munition percentage. `Wave.slots` can structurally represent more than one runtime line, but `UNKNOWN-MULTILINE-WAVE-COMBAT-SEMANTICS` prevents that uncalibrated state from entering rebuild, RR, targeting, or fire. A wholly reserve-only combat wave is not a preflight blocker merely because it could someday enter an occupied runtime line. Same-wave center-first refill/repack runs first; `UNKNOWN-CROSS-WAVE-FORMATION-REBUILD` is emitted only when a real physical slot is currently empty and an active reserve-only wave is eligible to occupy it. This requirement is checked both after round-start refill/repack and again immediately after combat casualties, before continuation or battle-termination evaluation, because combat itself may create the first vacancy. The post-combat check first projects the supported center-first refill of every wave into its own already-owned slots; a wave with empty owned slots and its own Reserve is therefore never mislabeled as a cross-wave candidate. Only vacancies remaining after that same-wave projection may require a different reserve-only wave. This defers the evidence boundary until cross-wave placement is actually required. Scheduled entry batches activate on their configured `arrival_round` as reserve/unit-state waves; if their arrival immediately requires an unimplemented placement into an open slot, the same deferred boundary is used. That arrival/boundary round is still recorded in `rounds_completed` and appended to `rounds` as a zero-casualty snapshot so round-page transport and Debug JSON can retrieve the arrival and boundary events for the exact round. Before an engagement has started, a side with no Round-0 battle-sustaining force is not declared defeated while it still has a future combat arrival whose native line is a main-line or configured fallback candidate. The simulator records `waiting_for_arrival` and advances to the scheduled arrival. If both sides are empty at Round 0 but both have future sustaining arrivals, the Round-0 event is combined with `side=null`, `pending_sides`, per-side `pending` details, and the earliest `next_arrival_round`. Non-sustaining future artillery/air/support does not postpone a Round-0 loss. Once both sides have reached a sustaining engagement, ordinary round-boundary termination remains authoritative and later reinforcements do not retroactively keep that battle alive. Future Cook arrivals still apply the named Experimental no-morale assumption when their effect becomes reachable. Doctor arrival alone no longer emits a no-healing assumption: healing is evaluated only at a round boundary that actually has eligible persistent Human damage. Support-assumption reach is recorded by side and round via `assumption_applied` events; a support batch scheduled beyond the simulated/reached rounds remains `not_reached`. `entry_batch_arrived.details.units` aggregates quantities by `unit_id` across all state waves in the same arrival batch so diagnostics/debug export report the full arriving force. Heavy/Light runtime-first formation is representable. Initial formation planning canonicalizes `Army.units` by each `ArmyUnit.formation_order_key` before assigning physical/damage positions, regardless of whether the caller used parsed dict input or constructed exported typed `Army` / `Scenario` objects directly; tuple insertion order is therefore not combat input. For native Long-range (`second`) and Artillery (`third`), `formation_order_key` is only a deterministic tie-break: each physical slot re-evaluates the strongest concrete candidate group by `min(remaining, slot_capacity) × primary weapon Damage`, matching strongest-first guidance plus observed partial-group behavior. A single-weapon Light runtime-first wave is executable: weapon selection uses its sole weapon while targeting uses runtime first-line priority. Round-start Light Infantry fallback has one additional executable subset: after all supported Heavy/same-unit compaction, a native-Light wave already on its native line may move wholly into currently open First slots when every surviving unit in that wave fits there. The move preserves wave-owned persistent damage and lets the ordinary RR pass redistribute it over the new single-line First placement. It never executes one state wave across two lines simultaneously. Exhausted Long-Range is separately supported: zero-ammo native Second remains empty, First vacancies use the secondary close/hull weapon, excess survivors remain Reserve, and partial state splits preserve RR-before-deployment-selection semantics. Mixed source unit types in one runtime formation are also executable through one shared row-major Attacking Matrix. Every source wave retains its own weapon, Workshop state and ammunition pool; each shot carries its concrete source damage-position column. A target formation's Am address book is computed before the first shot of that formation phase and shared/frozen across source waves only when they have the same weapon-specific penetrable target-wave set. Phase-start runtime-line membership is retained even if a promoted Light wave is eliminated mid-phase. If `ATK>DEF` eligibility differs, each distinct legal target set freezes its own address book; within that book, later shots still cannot renumber surviving target slots. `UNKNOWN-FALLBACK-LIGHT-INFANTRY-COMBAT` is limited to non-native Light without a uniquely selectable weapon. Native ranged combat selects primary and retains the existing wave ammo/partial-volley/exhaustion behavior. Exhausted Long-Range First fallback selects the secondary close/hull weapon; reactive secondary-weapon counterattack triggers while remaining in the native line are still unresolved.

`BattleReportFixture` remains backward compatible and optionally carries `fixture_id`, `evidence_class`, and `source_note`. Calibration evaluation resolves slot HP through the same combined player + Barbarian combat registry used by simulation, so supported Barbarian scenarios remain assessable for `damage_percent`. `evaluate_fixture(fixture, simulation_result)` and `run_fixture(fixture)` return `CalibrationResult`; `as_dict()` is JSON-serializable and includes simulation status, reached round, blockers, and ordered per-field assessments. Assessments are `match`, `mismatch`, or first-class `not_assessable`. Damage percent compares persistent integer damage with the documented round-up interval over surviving slot HP. Casualties use only same-round `damage` events addressed by `target_side`, `target_line`, and `target_damage_position`; those event fields are additive observability. Battle-report life percent is retained but returns `UNKNOWN-BATTLE-REPORT-LIFE-PERCENT-SEMANTICS`. Missing/ambiguous rounds or slots never fall back to another identity.


Browser knowledge/navigation contract: `戰鬥機制` and `Battle System PDF` are always-available top-level tabs independent of whether a simulation has run. Mechanics status is the user-facing accuracy/limitation register: known executable contracts, partial/calibration-required areas, and unknown boundaries must remain distinguishable. The source tab credits the empirical paper as *Ikariam Battle System* (AT Barbarossa, Xanto; 2020-07-16), links the original Gameforge forum thread, exposes the repository PDF through the stable `/ikariam-battle-system.pdf` path, and warns that its scenarios/tests predate version 13 so legacy numerical values are not treated as current data.

Browser debug-export contract: setup exposes JSON downloads above and below the army editor. The downloaded setup payload must be built by the exact same `scenarioFromSetup()` path used by `runSimulation()`, and includes the selected battlefield geometry plus combat chronology for diagnosis. The round report exposes a current-round JSON download containing the submitted scenario, summary result, exact current round snapshot, only that round's events, and explicit diagnostics (`unsupported_mechanics`, warnings, assumptions, report metadata). Deployment round 0 is downloadable as `ikariam-deployment-debug.json`. Exports are local browser files and must not include API keys or other credentials.

Browser battle-workbench contract: the Max rounds control defaults to 100 while allowing an explicit safety cap up to 1000; the player-facing UI must state that Cook morale is not yet fully modeled and must not present a common ~15-Cook player configuration as a verified fixed formula. Setup rows are metadata-driven. The default remains a lightweight one-front-line setup rather than silently pre-filling a large army. Built-in setup presets are UI-only helpers and the Presets panel is a collapsed-by-default `details` control: `simple` reproduces the lightweight front-line baseline, `combined` fills one unit type per executable land combat line with reserve depth plus Doctor/Cook support, and `player-vs-barbarian` exercises the separate Barbarian package; preset quantities must be derived from current battlefield geometry and unit size rather than copied slot constants. User-defined presets serialize the same setup configuration used to build a Scenario, but omit pinned profile versions and remain browser-local under versioned `localStorage`; loading must restore battle type/battlefield, policy, max rounds, defender Town Hall or Barbarian Village context plus wall level, per-side package, Forge, quantities, Workshop levels, and explicit entry batches. Clearing armies zeros quantities/removes extra batches while preserving the selected battlefield, settlement level, wall level, package, and Forge controls. The workbench exposes a Battle type layer (Land / Naval) which filters battlefield ids, while `battlefield` remains the Scenario source of truth. Each side independently selects an Army package (Player / Barbarian). Player rows expose quantity plus per-unit Workshop attack/armor levels and side-wide Forge/Hephaistos; Barbarian rows expose quantity only, hide/disable Workshop and Forge controls, use one fixed immediate batch, and display General Score 0. Browser defaults select Land / `land-max`, Player package, and Forge level 5 on both sides. The initial Hoplite quantity is derived from the selected default battlefield's first-line geometry and fills that line; this is a UI starting value only and does not alter Scenario or formation semantics. The ±slot helper is a setup aid, not a combat outcome: it derives one nominal increment as `floor(selected battlefield line.slot_space / unit.size)`, preferring the unit native line and using the existing Light Infantry first-line fallback only when that native line is absent. Manual quantities remain valid and need not be slot multiples. Entry-batch/wave identity remains available under advanced controls, and the same unit type may have multiple explicit batch rows; non-zero same-unit rows must have distinct `wave_id` values so their ammunition pools cannot be normalized together, while Workshop levels must agree for that unit type on the same side. Report views separate round replay from total casualty summary and render defender/attacker lines from canonical battlefield geometry rather than hard-coded slot counts. Land report presentation follows the in-game battle-board layout: the front row is left Flank | central First/Main line | right Flank, the Second/long-range line is centered behind it, and the rear row is Air defense (`anti-balloon`) | central Third/artillery line | Air bomber (`balloon`). The attacker renders rear → second → front toward the clash line, while the defender renders front → second → rear away from it. Flank physical positions are split into left/right visual groups only for rendering; this is presentation only and physical/damage positions remain engine-owned. If the selected battlefield has no flank geometry, the browser may show a no-flank reserve note for flank-native units; it must not fabricate flank slots. Player-mode reports must always expose unsupported-mechanic IDs, evidence warnings, experimental assumptions actually reached, ordinary reserve, and `deployed_support` as a separate support section. Research mode additionally exposes per-side `continuation_state`, raw waves/batches, and events for the currently loaded round page; it must not hide the player safety boundaries. The browser requests a summary first, then fetches/caches 10-round pages on demand so long battles do not require one giant HTTP response.

Military-score reporting is executable for current player land units through `military-economy-current`. Each player unit stores an unmodified resource score-basis total and a published General Score value; profile loading requires `general_score == resource_cost_basis_total / 50`. Workshop upgrades, Forge/Hephaistos and combat buffs never change that value. The player `military-economy-current` map remains player-only; Barbarian sides are assigned resource-cost basis 0 and General Score 0 by the battle-statistics package rule. Simulation output adds per-side `resource_cost_basis_lost`, `general_score_lost`, and `general_score_destroyed`; destroyed score is exactly the opposing side's loss. `combat_statistics.gross_damage_dealt` is a separate sum of emitted damage-event amounts and must not be described as military score.


Morale observability is additive and does not imply a morale algorithm. Every simulation result exposes `morale_status` with `modeled = false`, stable IDs `UNKNOWN-MORALE-SUPPORT` / `EXP-MORALE-NONE-001`, and per-side Cook counts. A side with no Cook reports `not_present`; strict mode with Cook reports `unsupported_boundary` only when the morale boundary is actually present in emitted unsupported events; experimental mode with Cook reports `ignored_by_named_assumption` only when `EXP-MORALE-NONE-001` is actually present in the result's applied assumptions. If another hard boundary stops the battle before the morale assumption is reached, Cook reports `not_reached`. `effect_applied` remains false in all current cases. The common practical reference of roughly 15 Cooks is explanatory only and must never be treated as a verified fixed no-morale-loss formula. The browser must surface this status in ordinary player-facing reports rather than requiring Research mode.


Combat/healing observability is additive and must distinguish the executable Doctor subset from unresolved partial allocation. Each pure-engine round snapshot exposes per-side `combat_statistics` with that round's `damage_dealt`, `damage_taken`, `healing`, and cumulative values. Damage is derived from emitted `damage` events; applied healing is derived from emitted `healing` events. Top-level `combat_statistics` exposes `gross_damage_dealt`, `gross_damage_taken`, `gross_healing`, and `engine_healing_applied`. With no Doctor, healing values are numeric zero. If an insufficient-capacity boundary reaches `EXP-HEAL-NONE-001`, true game healing is unknown from that round onward, so public `healing` / `gross_healing` become JSON null while `engine_healing_applied` still records any exact-subset healing actually applied before or alongside that unresolved boundary.

Every result also exposes `healing_status` with `modeled = false` plus `partial_model = true`, `model_status = EXACT_FULL_CLEAR_SUBSET_ONLY`, stable IDs `UNKNOWN-HEALING-ALLOCATION` / `EXP-HEAL-NONE-001`, the derived current capacity reference of 4000 per Doctor, and `capacity_is_allocation_formula = false`. The empirical timing contract is partial but useful: healing is a per-round effect reflected before the next round's combat; exact Healing-vs-RR ordering is unresolved. Land Doctor eligibility is Human combat units only; Machine units are excluded. The executable subset is deliberately order-invariant: if total Doctor capacity covers all persistent damage on every eligible Human combat wave, the engine clears all of that damage at the round boundary before the ordinary RR pass, emits a `healing` event, and reports `applied_exact_subset`. Its `affected_waves` diagnostics are a list of `{unit_id, wave_id, healing}` rows, using the canonical `(unit_id, wave_id)` unit-state identity so equal wave IDs on different unit types cannot collide. Because the result is all-zero eligible damage, unknown Healing/RR ordering and allocation priority cannot change it. If capacity is insufficient to clear all eligible Human persistent damage, Experimental emits `EXP-HEAL-NONE-001` / `healing_allocation_unresolved` and applies no partial healing rather than inventing wave/slot priority; Strict retains `UNKNOWN-HEALING-ALLOCATION`. Per-side status is `not_present`, `unsupported_boundary`, `applied_exact_subset`, `partial_allocation_unresolved`, or `not_reached`.


Formation chronology is an executable Art-of-Warfare contract distinct from formation filling order. Land filling order metadata is Air → Air defence → Artillery → Long-range → Close-combat → Flanks, while shot sequence is Air defence (`anti-balloon`) → Air (`balloon`) → Artillery (`third`) → Flanks (`flank`) → Long-range (`second`) → Main battle line (`first`). The same formation on both sides obtains firing eligibility from the same phase-start state. Casualties from an earlier formation phase immediately affect every later phase, but never cancel the opposing side's already-snapshotted shooters in the same formation phase.

Target priority is formation-owned and data-driven. For ordinary unit targets Artillery targets Main/First → Flank and must never silently target Long-range, Artillery, or Air; when an active Town Wall exists, Wall precedes Main/First. Strict keeps section-level wall combat guarded; Experimental executes the named/calibrated subset for penetration-eligible wall-first Artillery, breach exposure, flank lock, and exact divisible redistribution, with the remaining wall assumptions and guards stated above. Flank targets Flank → Long-range → Artillery → Main; Long-range targets Main → Flank → Long-range; Main targets Main → Long-range → Artillery → Flank; Air defence targets Air → Air defence; Air targets Artillery → Long-range → Main → Flank. Before a shot is spent, the selected weapon must have effective ATK strictly greater than the candidate's effective DEF. `ATK <= DEF` candidates are skipped without ammunition expenditure and selection continues down the ordinary priority list. Individual shots re-evaluate the highest surviving eligible target formation, allowing later shots to transfer after a higher-priority formation is eliminated.

**Generic Experimental kill resolution is sequential, with explicitly bounded exceptions.** Firing eligibility is frozen per side at formation-phase start; generic individual shots resolve in AM row order and casualties apply immediately. In the calibrated Naval first-round candidate cases only, the engine may replace the generic result for each physical target slot with a **pooled, integer-HP resolution** after gathering source volleys across waves in the same formation: `EXP-NAVAL-RAM-FOCUS-SHARE-001` uses a rational `F(Accuracy,6)` fraction of six nominal effective Barbarian Deckwrecker hits to focus pooled damage against six fresh player Ram hulls, spreading the remainder and discarding focal overkill; `EXP-NAVAL-DECK-OVERKILL-RETAIN-001` retains the nominal sequential D-kill discarded overkill as surviving wounds for the explicitly calibrated player Ram ATT20/Forge5 versus six fresh Barbarian Deckwrecker hulls. These candidate outcomes overwrite slot live units, persistent HP wounds, target-slot casualties, and casualty totals once for the shared physical AM, even if the same source formation is serialized into multiple waves. `damage` event entries for these cases are **aggregate synthetic pooled target-slot accounting**, not real Gameforge individual projectile/hit/miss or per-wave death attribution; diagnostics include `experimental_pooled_allocation_not_real_shot_trace=true`, `pooled_source_wave_count`, `pooled_group_count`, and `pooled_casualties_not_individual_wave_attribution=true` plus the applied candidate rule ID. A separate `EXP-NAVAL-FAST-CARRIER-74PCT-001` candidate chooses individual-target focus using a **74% remaining-hull-HP threshold** for narrowly calibrated first-round two-by-three Carrier formations against 30 eligible primary-armed Fast Boats and specifically documented Forge/Workshop tuples: its actual weapon Accuracy stays 90/95, its per-wave damage events are **not** the pooled Ram override, and ineligible tuples, later rounds and other geometries retain generic fallback. These three rules are labeled Experimental in-sample hypotheses, **not official Gameforge algorithms**; Strict does not inherit these candidates. The Swordsman formation-level exception below remains independent of naval overrides. The official Accuracy algorithm remains unknown, and `EXP-ACCURACY-CONCENTRATION-001` remains a separate within-slot target-selection hypothesis. The generic fallback is sequential D-kill/overkill-discard. Swordsman-vs-Swordsman flank additionally has a formation-scope Experimental selector driven by the merged reduced-Am source-column counts, so splitting one formation across multiple entry waves cannot change the result. All-even source columns remain generic D-kill. Exact aggregate divisibility may use `EXP-SWORDSMAN-FLANK-IKILL-EXACT-DIVISION-001`. The current modern M-kill candidate `EXP-SWORDSMAN-SYMMETRIC-2HIT-ROW-PM-MKILL-001` is limited to six 7-hit source columns in the two-hit regime: after generic D-kill, one lethal-pair overkill per AM row is retained into an M-pool and combined with generic persistent damage, then the pool is converted into extra casualties and residual damage. This is a calibration hypothesis, not an official formula. Accuracy is retained in diagnostics as a possible higher-level selector because the empirical study explicitly proposed links to IR and D-kill count per column but did not solve them. P-kill, IR-kill, PIR-kill and other M-kill shapes remain open. The bounded M-kill selector also requires a full six-slot source formation and a reciprocal two-hit regime; the 2026-10-02 asymmetric 2-hit/3-hit Swordsman observation is deliberately left on the generic baseline rather than forced through the older calibration. IR and SR have explicit algorithm hooks, but their selectors remain unknown; `EXP-IR-DISABLED-001` and `EXP-SR-DISABLED-001` state that their triggers currently return false. PDF RR determines wave-to-slot aggregate persistent damage; exact within-slot individual allocation remains open, so `EXP-SLOT-DAMAGE-EVEN-001` is named when non-zero aggregate damage is materialized evenly for sequential resolution.

Current land-unit metadata exposes the in-game Human/Machine classification as `unit_class`. Human: Spearman, Swordsman, Hoplite, Spartan, Slinger, Archer, Sulphur Carabineer, Doctor and Cook. Machine: Steam Giant, Battering Ram, Catapult, Mortar, Gyrocopter and Bombardier. Doctor healing eligibility uses this Human/Machine distinction directly. The order-invariant full-clear subset is executable; only partial-capacity wave/slot allocation and exact Healing/RR ordering remain unresolved. Naval Tender eligibility is documented separately from land Human/Machine classification.


Am slot addressing is stable across one runtime formation firing phase. When that source formation first targets a target formation class, the target class's currently occupied damage-position slots are frozen as one shared address set for every source wave/unit type in that phase. Row modulo is evaluated against that frozen set while the target class survives. If an addressed slot becomes empty mid-phase, a later row—including a shot from a different source unit in the same runtime formation—still addresses that original position; it is not redirected to another surviving slot, and the engine emits `shot_addressed_empty_slot`. This does not disable Art-of-Warfare formation-class target transfer: after the entire higher-priority target formation is eliminated, later shots may select the next formation class and establish a new frozen address set there.


Round-boundary same-wave placement is center-first and precedes RR. Within a wave's already-existing runtime slots, deployed survivors plus that wave's Reserve are re-packed in ascending damage position; because the empirical physical labels encode center-first order, this moves surviving units back toward the center before persistent damage is redistributed. This rebuild never creates a slot, crosses runtime lines, or borrows units from another wave, so the existing cross-wave and multi-line guards remain intact.

Battle-report presentation state is additive and engine-derived. Every wave snapshot exposes `reserve_damage` and `reserve_hit_points_percent`; the percentage is the surviving Reserve group's aggregate HP ratio within that one entry batch, computed from `reserve * unit_hp - reserve_damage`, and never merges damage across batches. Every slot snapshot exposes current-round `casualties`; a slot that reaches zero survivors remains present with its unit identity and `hit_points_percent = 0` so the browser can render the destroyed slot rather than turning it into a never-used empty position. Slot casualties are round-local display observability, while top-level casualties remain battle totals.

The browser battle report renders occupied and destroyed slots with unit art, a vertical surviving-HP bar, and `alive (-round casualties)`. Destroyed slots retain the unit icon in a visually dimmed/grayscale state with a 0% red HP rail only for the round in which that slot records casualties. A later round omits a still-empty zero-unit slot so the physical position renders empty; normal same-wave Reserve refill renders the new live state. Reserve is rendered as icon cards. Multiple entry batches of the same unit type are aggregated only for the player-facing Reserve card using total remaining Reserve HP divided by total maximum Reserve HP; Research/tooltip detail preserves each batch's quantity, persistent damage, HP percentage, and munition percentage.

Round navigation treats deployment as a separate `初始部署` control, not a numbered round. Numbered navigation provides first/previous, at most nine round buttons centered on the current round when possible, next/last, and direct numeric round jump. Setup rows provide one global, default-collapsed `顯示兵種數值` control; when expanded, each row displays current HP plus attack/defense derived from the unit's public numerical metadata, that row's Workshop levels, and the side-wide Forge level. The browser consumes API-provided Workshop increments and Forge effects rather than hard-coding upgrade constants.


The setup workbench hides unit name/basic metadata by default behind the global `showUnitIdentity` control while keeping icons and controls visible; the separate stat preview may wrap HP/ATK/DEF and its Workshop/Forge note. Battlefield slot faces omit repeated unit names. Battlefield and Reserve detail use one body-level fixed floating tooltip, positioned from the trigger rectangle and clamped/flipped to the viewport so parent overflow cannot clip it.


### RR-before-deployment-selection invariant

Persistent damage is wave-owned. Every supported refill/repack/handoff/fallback preserves the complete surviving wave as the RR population before deployment selection. Ordinary placement parks aggregate damage until final RR; a true state split materializes the selected segment's proportional RR share using the same allocator. Same-unit waves from different state/batch identities retain separate ammo and damage pools unless an explicit handoff contract says otherwise.
