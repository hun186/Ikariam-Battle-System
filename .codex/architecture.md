# Architecture

Scenario models unit-specific Workshop upgrades and side Forge; registry models domain, role/support effect, semantic class, native line, size, and per-weapon accuracy/ammo. Packaged mechanics, units, Workshop, Forge, support, formation, targeting, battle-end, and calibration data load through `importlib.resources`. An immutable registry provides all five executable land geometries and five screenshot-backed naval geometries as the single authority for slot space and deployment order; community slot geometry and empirical damage-position evidence retain distinct provenance. Battlefield choice is explicit scenario input and acts as the normal/baseline geometry. Town Hall ranges themselves are metadata, but configured settlement/garrison state can select `land-max` as the effective initial open-field geometry and suppress the wall. Mid-battle threshold crossings are detected and guarded before uncalibrated cross-geometry remapping. The pure planner validates and executes profile eligibility, fallback eligibility, and Heavy-before-Light/front-before-flank precedence, assigning runtime `Slot.line` without mutating native metadata. The formation layer also exposes eligible runtime lines so safety checks consume the same native/fallback contract rather than duplicating it. Art of Warfare target priority is a known runtime-line role contract. A weapon-specific eligibility layer now runs before AM address selection: `target_eligibility.py` compares effective ATK with effective DEF and excludes `ATK <= DEF` candidates without consuming ammunition, allowing selection to continue to the next priority target. The independent weapon-selection layer preserves primary weapons for native combat and selects the sole registry weapon for runtime-first Light Infantry; damage calculation consumes that selected weapon and reports its ID/trigger. Experimental Accuracy selection is a separate within-slot layer after AM slot addressing and damage calculation: `accuracy.py` deterministically chooses a survivor from the addressed slot using the weapon Accuracy / remaining-HP threshold hypothesis, leaving slot addressing and damage arithmetic untouched. Exhausted Long-Range multi-weapon fallback is supported: zero-ammo native Second stays empty, open First uses the secondary close/hull weapon, excess survivors remain Reserve, and RR precedes deployment selection. Reactive secondary-weapon counterattack triggers remain unresolved. Mixed runtime formations are executable through one shared row-major Attacking Matrix: each concrete wave keeps its own weapon, upgrades and ammunition pool, source slots contribute columns ordered by runtime damage position, and target slot addresses and runtime-line membership are frozen at formation-phase start per target formation plus penetrable target-wave set. Source waves with identical eligibility share one book; different penetration sets freeze separately, and mid-phase casualties cannot shrink either book. Multi-line `Wave` execution remains guarded as `UNKNOWN-MULTILINE-WAVE-COMBAT-SEMANTICS`; wholly reserve-only waves eligible for an occupied runtime line are guarded as `UNKNOWN-CROSS-WAVE-FORMATION-REBUILD`. Round-start same-wave formation rebuild precedes RR.

Battle-report calibration is an executable layer beside, not inside, combat mechanics. `run_fixture()` invokes the engine and delegates to `evaluate_fixture()`, which consumes JSON-shaped snapshots/events. It addresses slots by side/runtime line/damage position, resolves unit HP through the fixture profile, and uses additive damage-event target identity for exact-slot casualty aggregation. Independent field assessments preserve explicit unknowns; a calibration match never promotes evidence into a production rule.


The browser is now treated as a battle workbench with three presentation states: setup, round replay, and total report. Setup consumes canonical unit/battlefield metadata and converts only non-zero rows into the existing Scenario contract; combat rules remain exclusively in the engine. Round rendering mirrors the two sides around the contact line with attacker above and defender below, keeps reserves separate, and derives every visible line/slot from battlefield metadata. The engine's round-0 deployment snapshot is preserved for inspection but labeled `部署` in the pager so it is not confused with an in-game battle round. Total reporting now adds an evidence-backed land military-economy layer without changing combat math. The economy profile stores each player's unmodified resource score basis and validates `General Score = basis / 50`; the public simulator wrapper derives score lost/destroyed from casualties after core combat returns. Gross damage reporting is separately derived by summing emitted damage events and is explicitly not conflated with military score.


HTTP battle transport is intentionally separate from the pure combat engine. `ikariam_battle.simulate()` still produces a complete deterministic in-memory report for internal callers and calibration. `web_simulator.run_battle()`, shared by the ASGI and Vercel adapters, projects that full report into either a compact summary or a bounded round page. The browser stores the submitted Scenario locally, requests summary first, and deterministically replays the same Scenario for 10-round pages as the user navigates. Loaded pages are cached client-side; no server-side battle session is required, which keeps the serverless deployment stateless while bounding response payload size.


Browser simulation requests distinguish the last successfully committed battle from a pending replacement. The active `simulationGeneration` and its scenario/page cache remain intact while a newer summary request is pending; a separate monotonic request generation suppresses stale overlapping summaries. Only a successful latest summary atomically becomes the active generation and replaces the scenario/cache. If the pending request fails, report navigation is re-enabled for the prior completed battle instead of discarding it.


RR is a formation-state invariant rather than a Long-Range rule. Slot placement code must not decide damage ownership from the pre-repack slots. It first preserves aggregate persistent damage on the concrete wave, performs supported placement, then lets RR allocate the final deployed/Reserve shares. If placement creates a second state-wave object, the split helper materializes the proportional RR share against the original surviving population before the new state is detached.
