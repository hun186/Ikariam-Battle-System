# Ikariam Battle Simulator — evidence-aware Phase A

A deterministic browser simulator combining current Infinite Horizons numerical profiles with empirically reconstructed battle mechanics. It is not official Gameforge source code; strict mode refuses unresolved mechanics and experimental mode exposes every named assumption.

## Current profiles

- Complete land and naval HP, damage, armor, accuracy, ammunition, size, and primary/secondary weapons from a reviewer-verified current community reference; naval values also carry Gameforge forum player-test corroboration.
- v14 Workshop: unit-type-specific upgrades, land +5 and naval +10 per level. Levels are non-negative integers and can differ between Hoplites, Swordsmen, and other unit types on the same side.
- v14 Forge: side-wide levels 0–5.
- v17 support: Doctor/Tender healing ×20; 4000 is derived from legacy 200. Doctor healing is partially executable for the order-invariant full-clear case; partial-capacity allocation and exact Healing/RR ordering remain unknown. Cook morale remains unresolved.
- Legacy empirical mechanics profile for Am and RR; Art of Warfare firing chronology and formation target priorities are executable, while SR/IR triggers and special kill selection remain unresolved.
- Legacy/community battle-end profile distinguishes actual main-line holders, unresolved light/long-range fallback candidates, and definitely non-sustaining artillery, air, and support.
- Current land military-economy profile derives General Score from the unmodified resource score basis at 1 point per 50 resources; Workshop, Forge, and combat buffs do not change score value.

Official changelog claims and exact community/PTS tables are not conflated. The reviewer verified sources through v17.5.0 with retrieval date 2026-09-24; this environment did not independently open those URLs. See [the evidence register](docs/mechanics-spec.md).

## Operational scope

All five land battlefield geometries are executable through explicit scenario IDs: `land-mini` (Town Hall 1–4), `land-small` (5–9), `land-medium` (10–16), `land-large` (17–24), and `land-max` (25+). The battlefield selector remains the explicit normal/baseline geometry for backward compatibility. Player defenders can enter Town Hall Lv1–66 and Town Wall Lv0–48; when settlement context is configured, garrison state may override the effective battle geometry to `land-max` open field. When Town Hall is configured, the engine computes land garrison limit as `250 + 50 × (Town Hall + Wall)`, counts unit quantities rather than unit Size, excludes Doctor/Cook per v17.4.0, and starts over-limit defenses on `land-max` with the wall suppressed. Barbarian defenders may provide Village Lv1–50; the current 2024 Gameforge-forum community rule is `(Village + Wall + 5) × 50`, with the older `≈250 + 75 × wall` retained only as a historical approximation. The selected battlefield remains the normal/baseline geometry. Capacity is `floor(slot_space / unit size)`, not a unit constant, and the browser renders line/slot counts from the selected battlefield geometry. Battlefield metadata carries an explicit `domain`; the browser exposes a Land/Naval layer, while the battlefield ID remains the executable source of truth. `naval-max` is executable with the current official/community formation, targeting, ammunition, RR, Tender full-clear, and Barbarian Fleet numeric contracts; smaller naval geometries remain reserved until independently verified. Initial land formation supports the evidence-backed Heavy-before-Light rules and homogeneous single-weapon Light Infantry fallback already modeled. Round-start rebuild supports a whole native Light Infantry wave moving into open First slots when all of that wave fits there. Exhausted Long-Range waves on land and naval fields also move to First with their secondary/close weapon: when only part fits, the promoted First-line state is split out and excess survivors remain in Reserve with RR-preserved damage. Partial First+Flank Light splitting, unrelated cross-wave rebuilds, and reactive secondary-weapon trigger semantics remain guarded rather than guessed.

Ammunition is pooled as shots across deployed and reserve units of a wave. Art of Warfare firing order and runtime-line target priorities are executable: same formations on both sides obtain firing eligibility simultaneously, earlier formation casualties suppress later firing, and individual shots may transfer to the next target formation only after the higher-priority formation is eliminated. Mixed unit types sharing one runtime formation contribute separate source columns to one row-major Attacking Matrix while retaining their own weapons, upgrades and ammunition pools. The target Am row→slot address set stays frozen across the entire source formation phase for source waves that share the same penetrable target-wave set; if weapon-specific `ATK>DEF` eligibility differs, each distinct legal set freezes its own book. An emptied addressed slot does not cause later rows using that book to remap onto surviving slots. Accuracy is per weapon. The official algorithm remains unresolved, so Strict still blocks on `UNKNOWN-ACCURACY`; Experimental uses the explicit `EXP-ACCURACY-CONCENTRATION-001` hypothesis: Accuracy is a deterministic within-slot concentration threshold, not Bernoulli hit/miss. One-shot-capable hits never manufacture misses; otherwise damage spreads to healthier survivors until the most-damaged survivor's remaining HP% is at or below Accuracy, then fire focuses that survivor. Target eligibility is evaluated before a shot is spent: a weapon attacks only when its effective ATK is strictly greater than the candidate target's effective DEF; `ATK <= DEF` candidates are skipped without ammunition expenditure and selection continues down the normal target-priority list. Doctor/Tender healing and Cook morale have separate boundaries and are represented as deployed support rather than ordinary reserve. For land Doctor healing, the engine now applies the exact full-clear subset at the round boundary when total Doctor capacity covers all eligible Human persistent damage; capacity-shortfall allocation remains explicit/unknown rather than guessed.

Each side independently selects an army package. `army_kind=player` uses the normal player registry. `army_kind=barbarian` uses the nine Barbarian Village land units already documented by the project; Barbarian and player unit IDs cannot be mixed on one side. Clubman is Heavy Infantry on the First line even though part of its current numeric derivation references Spearman equivalence. Barbarian armies are modeled with no Workshop upgrades, Forge level 0, one immediate entry batch, one wave per unit type, and zero General Score/resource-basis accounting. Quantities are manual: the simulator does not yet generate a complete village garrison from Barbarian Village level.

This remains a **unit-vs-unit Phase A** simulator. Town Wall input plus current Infinite Horizons per-section HP/Armor (`1800 + 900×Lv`, `72×Lv`) and Damage (legacy three-tier wall table ×18; observed Lv1=216, Lv9=504, Lv18=2160, Lv26=5580) and initial garrison-driven open-field escalation are represented. Wall target priority is now recorded as Artillery → Wall before ordinary First-line targets, and the same strict `effective ATK > effective DEF` penetration rule is available for wall arithmetic; however current wall Accuracy, section-level shot allocation/damage application, executable segment breaching and defender refill, flank locking, automatic Barbarian army/wall generation, calibrated mid-battle cross-geometry state transfer, and complete city-battle behavior are not implemented. An active positive `wall_level` stops explicitly at `UNKNOWN-TOWN-WALL-COMBAT`. If an open-field battle later falls back under the garrison limit, the engine detects the exact threshold crossing but stops at `UNKNOWN-GARRISON-BATTLEFIELD-TRANSITION` before shrinking geometry or reintroducing the wall, because cross-geometry wave/slot/damage/ammo transfer is not yet calibrated. Barbarian garrison threshold is executable when Village level is configured, using the 2024 forum formula with explicit community provenance. The older wall-only guide expression remains documented as an approximation, not an equal-confidence competing formula.

Snapshots keep all survivors in `total` and expose `main_line_holding_total`, `fallback_candidate_total`, and `continuation_state`. A `fallback_required` state first projects the supported Light→First and exhausted Long-Range→First moves; if that restores First, the next round continues from the rebuilt formation. Exhausted Long-Range fallback supports both whole-wave promotion and partial First fill with the excess kept in Reserve. The engine still stops inconclusive for unsupported partial/multi-line Light fallback, unrelated cross-wave rebuilding, reactive secondary-weapon trigger semantics, or other unresolved fallback states and never fires another round from stale positions. Artillery, air, and support survivors withdraw/scatter without becoming casualties when the opponent retains a main line. A simultaneous both-no-main-line outcome remains unknown rather than being silently called a draw.

## Run and verify

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
pip install -e .
pytest -q
uvicorn asgi:application --host 127.0.0.1 --port 8000
```

The browser obtains profiles, battlefield geometry/domain, Forge effects, player units, Barbarian units, unit roles/lines, and unit size from `GET /api/simulate`. The setup screen first selects battle type, then a per-side army package. Player rows expose quantity, per-unit attack/armor Workshop levels, ±one-slot helpers, and advanced entry-batch controls; Forge/Hephaistos stays side-wide. Barbarian rows expose quantity/slot helpers only and suppress controls that do not apply. The default setup stays intentionally small, while the collapsed-by-default Presets panel can fill a geometry-derived multi-line Player-vs-Player test or Player-vs-Barbarian test. Users can also save, load, overwrite, and delete named setup presets in browser `localStorage`; those presets are local to that browser and use the same setup serializer as simulation, so quantities, upgrades, Forge, package choice, battlefield, and entry batches round-trip together. A dedicated clear action zeros both armies without changing the selected battlefield/package/Forge. Results are split into round replay and total summary views. The summary reports unit casualties, General Score lost/destroyed, and gross engine damage separately.

```bash
curl -X POST http://127.0.0.1:8000/api/simulate -H 'Content-Type: application/json' --data @sample_scenario.json
python simulator.py --scenario sample_scenario.json
```
