# Mechanics and current-data evidence register

The simulator combines empirical mechanics with current numerical profiles; it is not Gameforge source code. The primary empirical paper is *Ikariam Battle System* (AT Barbarossa, Xanto; 2020-07-16), originally shared by AT Barbarossa in the Gameforge EN forum thread `https://forum.ikariam.gameforge.com/forum/thread/43268-ikariam-battle-system/`. The paper's own/forum warning that its scenarios and tests predate version 13 is preserved: it is an algorithmic/evidence source, not authority for current unit numbers. Evidence classes remain separate: `OFFICIAL_CHANGELOG`, `GAMEFORGE_FORUM_PLAYER_TEST`, `COMMUNITY_PTS_TESTED`, `COMMUNITY_REFERENCE_CURRENT`, `USER_PROVIDED_BATTLE_OBSERVATION`, `EMPIRICAL_PAPER`, `DERIVED`, `HYPOTHESIS`, and `UNKNOWN`. A user observation is real calibration input but is **not** an official specification. Sources verified by the reviewer are marked `REVIEWER_WEB_VERIFIED`, not `CODEX_NETWORK_VERIFIED`.

## Formation and runtime roles

Formation is separate from combat: planning establishes runtime lines, weapon eligibility is selected separately, runtime source line selects target-line priority, the Attacking Matrix distributes attacks among target slots, and only then do damage, kills, and redistribution occur. The Attacking Matrix never decides which units enter a line.

The versioned `formation-land` profile distinguishes tactical `semantic_class`, preferred `native_line`, compatibility-only `battlefield_class`, and authoritative runtime `Slot.line`. Its first-line eligible classes, precedence, and fallback classes are executable planner inputs and are validated for consistency. For first line, Heavy precedes eligible Light. A native-first Light remains eligible independently of fallback; a native-flank Light may enter first only when its semantic class is explicitly fallback-eligible. A partial Heavy batch owns its slot (one slot never mixes types/batches), Light fills only other front slots, and front allocation occurs before remaining Light can enter its native flank. The pure planner calculates this rule and never mutates registry metadata. Thus a Swordsman remains native flank while its planned runtime line can be `first`.

The paper's standard physical damage-label layouts are first/second `[6, 4, 2, 1, 3, 5, 7]`, third `[5, 3, 1, 2, 4]`, flank `[6, 4, 2, 1, 3, 5]`, balloon `[1, 2]`, and anti-balloon `[2, 1]`. Each geometry uses the specified centered subset, except that one-slot anti-balloon retains the existing `(1,)` compatibility label. These arrays remain `EMPIRICAL_PAPER` evidence, distinct from the community slot geometry. The formation profile explicitly delegates executable deployment order to `battlefield_geometry.damage_priority`; the planner validates that authority and refuses an unsupported alternative. Each battlefield geometry is the single executable source for its center-first deployment order while storing physical position separately. Non-standard renumbering remains unresolved.

Formation legality is not combat knowledge. Separate unit types may coexist in one runtime formation while each physical slot still has exactly one concrete unit-state owner, and snapshots serialize native plus runtime lines. Formation planning first orders unit-state rows by `ArmyUnit.formation_order_key`, so directly constructed typed armies and parsed dict armies have the same deterministic placement regardless of caller tuple order. Weapon selection is an explicit step: native combat retains its primary weapon, while a non-native runtime-first Light with exactly one registry weapon deterministically uses that weapon. The empirical paper's Attacking Matrix explicitly models a formation whose source columns contain different unit types and slot heights. The engine therefore merges all source waves in one runtime formation into a shared row-major Am: each wave keeps its own weapon/upgrades/ammunition, source damage position supplies deterministic column order, and the target address book is frozen **before the first shot of the formation phase** per target formation and penetrable target-wave set. Runtime-line membership and slot addresses are therefore phase-start facts: a promoted Light wave that dies mid-phase remains represented by its now-empty frozen address rather than reverting to native-line membership and shrinking the book. Source waves whose weapon/upgrades yield the same legal target set share one frozen book; weapons with different penetration eligibility use separate frozen books without changing the shared row-major source ordering. `UNKNOWN-FALLBACK-LIGHT-INFANTRY-COMBAT` is limited to a non-native Light whose weapon is not uniquely selectable. `UNKNOWN-MULTILINE-WAVE-COMBAT-SEMANTICS`, `UNKNOWN-FALLBACK-LONG-RANGE-WEAPON`, and `UNKNOWN-SECONDARY-WEAPON-TRIGGER` remain protected. RR slot-internal individual allocation, IR/SR trigger conditions, special kill-type selectors, and secondary-weapon selection remain unresolved. Firing chronology and formation target priority are established separately by the Art of Warfare help contract described below.

### Formation filling, firing chronology, and target priority

Formation **filling order** and **shot sequence** are separate Art of Warfare rules. Land formation filling order is Air → Air defence → Artillery → Long-range combat → Close-combat → Flanks. Land shot sequence is Air defence (`anti-balloon`) → Air (`balloon`) → Artillery (`third`) → Flanks (`flank`) → Long-range (`second`) → Main battle line (`first`).

The same formation on both sides shoots simultaneously. The engine therefore snapshots both sides' firing eligibility at the start of each formation phase. Casualties caused in one formation phase immediately suppress firing in every later phase, but a casualty resolved while processing one side of a phase cannot cancel the opposing side's already-snapshotted firing eligibility in that same formation phase.

Formation target priority is also executable and belongs to runtime line, not unit identity:

- Artillery / `third`: with an active Town Wall, Wall is the first target; unit-vs-unit priority after/no Wall remains Main/First → Flank.
- Flank: Flank → Long-range/Second → Artillery/Third → Main/First.
- Long-range / `second`: Main/First → Flank → Long-range/Second.
- Main / `first`: Main/First → Long-range/Second → Artillery/Third → Flank.
- Air defence / `anti-balloon`: Air/Balloon → Air defence.
- Air / `balloon`: Artillery/Third → Long-range/Second → Main/First → Flank.

Before a shot is committed, each candidate target is filtered by weapon-specific penetration eligibility. The selected weapon's effective ATK (base + Workshop, then Forge damage multiplier) must be **strictly greater** than the candidate's effective DEF (base Armor + Workshop armor + Forge armor). `ATK <= DEF` is not a zero-damage shot: that candidate is skipped without ammunition expenditure and target selection continues to the next damageable candidate/formation. Individual shots then re-evaluate the highest surviving eligible target formation. Once a higher-priority formation is eliminated, later shots in the same firing phase may transfer to the next listed formation. This is **formation-class transfer only**. When an eligible target formation is first selected, its Am row→damage-position address set is frozen for the source waves that share that same penetrable target-wave set. Different source weapons in one runtime formation may therefore hold different frozen address books only when their `ATK>DEF` eligibility sets differ. If an addressed slot empties mid-phase, later rows that still address that slot are not remapped to surviving slots; the shot remains addressed to the empty slot and deals no damage. Only when the whole target formation is gone may a later shot transfer to the next formation class. Artillery therefore never silently attacks Long-range, Artillery, or Air: if neither Main nor Flank remains, it has no valid target.

At round boundary, `_prepare_round_start()` first re-establishes each wave's own existing placements through `_rebuild_formation()`. It then performs two narrow formation-level compactions before RR. First, Heavy Infantry waves from the **same entry batch** may compact across that batch's already-owned First-line physical slots, allowing mixed Hoplite / Steam Giant ownership to move inward center-first without mixing unit types inside one slot. Second, waves with the **same `unit_id`** may compact across that unit's already-owned slots on the **same runtime line**, even when the waves belong to different entry batches. The second rule is ordered by arrival round / batch / wave, may move an already-deployed later wave inward, and allows a reserve-only later wave to take over emptied slots only on its native line. Ammo, persistent damage, Workshop upgrades, and wave identity remain independent per concrete wave; no ammunition pool is combined or loaned. Both rules reuse existing physical slots and derive capacity from the occupying unit size. RR runs **after** both compactions so each wave's total persistent damage is conserved and redistributed over its final slots. Different-unit cross-entry-batch replacement, Light Infantry fallback, cross-runtime-line placement, and creation of new physical slots remain unsupported.

A reserve-only combat wave is not itself evidence that cross-wave rebuilding is needed. At each round boundary, existing waves first center-pack and refill from their own Reserve, then the supported same-entry-batch mixed-Heavy First-line compaction and same-unit same-line cross-wave compaction are projected. A later Sulphur Carabineer entry batch may therefore take over emptied `second` slots from an earlier Sulphur Carabineer wave while keeping a separate ammunition pool; likewise a later Steam Giant wave may take over existing Steam Giant `first` slots. `UNKNOWN-CROSS-WAVE-FORMATION-REBUILD` is reserved for placements still outside these rules, such as a different unit type from another entry batch or Light Infantry fallback. If an arrival reaches that unsupported boundary before firing, the round is still recorded in `rounds_completed` and appended as a zero-casualty state snapshot so API paging and Debug JSON retain the arrival and boundary events. The same requirement is re-evaluated after each round's volleys and casualties, before fallback/continuation/termination logic. That post-combat evaluation globally projects supported same-wave refill **and all supported same-batch Heavy-Infantry handoffs first**, so an unrelated reserve wave cannot claim a slot that a supported handoff will already occupy. Only vacancies that remain after those projections may trigger the unsupported boundary. If the just-completed round has emptied the current First line but a supported same-batch Heavy-Infantry handoff is available for the next round, continuation is projected as sustaining for battle-end evaluation only; the completed-round snapshot is left unchanged and the actual slot transfer still occurs at the next round start. The same pending-handoff projection also applies at the `max_rounds` horizon, so reaching the safety limit cannot turn a still-available supported replacement into a false defeat; the result remains inconclusive instead. A single wave's ordinary reserve refill remains supported; unrelated-line reserves and support units are not cross-wave candidates.

When a runtime formation is mixed (for example Hoplite plus Steam Giant on First, or Ram plus Catapult on Third), target selection remains formation-priority based. The addressed damage-position set is built across all deployed target waves in that runtime formation, while damage/armor/persistent-damage ownership remains attached to each concrete target wave and slot. On the source side, different unit waves contribute columns to one row-major Attacking Matrix and retain independent weapons, upgrades and ammunition pools. Public `attacking_matrix` traces remain emitted per concrete source/target-wave relationship: the event includes `target_wave`, `trace.target_damage_positions` contains only positions owned by that target wave, and `trace.formation_target_damage_positions` records the frozen address set for the whole target formation.

## Workshop and Forge ownership

Workshop levels belong to a player’s **unit type**, not the whole army. Every `ArmyUnit` has `attack_upgrade` and `armor_upgrade`; all rows/waves of the same `unit_id` on one side must agree. Duplicate rows aggregate only when unit, wave, and upgrades agree. Forge remains side-wide at level 0–5.

### Battle domain and army packages

Battlefield id is the executable domain authority. Current executable ids are the five `land-*` geometries; metadata also exposes a reserved `naval-mini` row with `domain = naval` and `supported = false` so the UI can present a Land/Naval layer without claiming naval geometry is implemented. No separate Scenario battle-domain field is introduced, avoiding contradictory states such as a naval domain paired with `land-max`.

Each side has `army_kind = player | barbarian` (default `player`). Unit definitions carry the corresponding package identity, and deployment rejects a unit id from the wrong package. Player-vs-Barbarian and Barbarian-vs-Barbarian land battles are therefore valid, while player and Barbarian units cannot be mixed on the same side.

The Barbarian package uses the existing nine-unit `barbarian-village-current` profile as combat definitions. Its HP/armour/damage/accuracy/ammunition/size evidence remains exactly the profile’s documented derived/current evidence; promoting the catalog to simulation does not upgrade that evidence class. Clubman is explicitly Heavy Infantry on the First line; its documented Spearman equivalence is used for numeric derivation only and does not determine tactical class. Barbarian armies have no Workshop upgrades, use Forge 0, arrive in one immediate batch, cannot split one unit type across multiple waves, and count as zero resource score basis / zero General Score. The browser hides player-only controls for that package. Exact village-level garrison quantities, walls, morale/retaliation and automatic village-level generation remain outside this contract.

The safe single-section breach arithmetic is `ceil(HP / (successful-hit damage − Armor))`; it does not convert directly to deployed mortar count because accuracy/shot allocation are still unresolved. The v13 PTS correction for levels 10–20 is reflected by requiring the post-fix/current damage points rather than relying on the earlier beta snapshot. Wall target priority and penetration eligibility are now established: attacking land Artillery prefers Wall before ordinary First-line targets, and a weapon that cannot exceed wall Armor is ineligible rather than wasting a shot. Wall combat still stops at `UNKNOWN-TOWN-WALL-COMBAT` because section-level shot allocation, wall Accuracy interaction, HP application/breach, defender refill, and flank-lock release remain unresolved. Configured Barbarian defenders use the 2024 Gameforge-forum community formula `(Village + Wall + 5) × 50`; the older wall-only expression is retained as an approximation. The same strict `counted defenders > limit` open-field trigger and `<= limit` return trigger apply.

A line stores `slot_space`, not a unit capacity. Deployment uses `floor(slot_space / unit.size)`. With slot space 30 this yields Hoplite 30, Steam Giant 10, Carabineer 7, and Catapult 6. Slots retain physical position and damage position separately. Am targets ascending damage positions; only vector export uses physical order. At round start the following-round formation refills before RR computes `D/N*s`. RR uses the explicit experimental half-up tie policy `EXP-RR-ROUND-HALF-UP-001`, follows damage priority, and preserves deployed + reserve wave damage; this is not claimed as Ikariam truth.

Only deployed waves (`any(slot.units > 0)`) are targetable; reserve-only and destroyed waves are skipped. Art of Warfare line-role priority is modeled as a known contract: target priority derives from runtime `Slot.line`; native line is only a reserve-only internal compatibility fallback. Weapon selection remains a separate responsibility: a runtime-first Swordsman uses its sole `primary` weapon, while its target priority comes from `targeting.priorities["first"]`. Multi-weapon ranged fallback and secondary triggers remain unknown. If a completed round requires an unimplemented cross-wave rebuild (including long-range fallback), both policies stop inconclusive with `UNKNOWN-FORMATION-FALLBACK`; neither continues firing from stale positions.

## Ammunition, targeting, accuracy, and support boundaries

### Entry-batch ammunition semantics

An arrival batch is identified by `entry_batch_id` and may contain many unit types that enter together. Each unit type inside that arrival batch has its own unit-state `wave_id`, because ammunition and persistent damage must not be shared across different unit types. Since formation and runtime state use `(unit_id, wave_id)` as state identity, the same pair is rejected if explicitly reused across different entry batches; repeated rows inside the same entry batch/state identity may aggregate. Missing identity fields retain backward-compatible defaults, but a present `wave_id` or `entry_batch_id` must be a non-empty string and is never silently treated as absent. Finite ammunition is therefore owned by one unit-state wave, never by the whole arrival batch, side, slot, or individual soldier. Its normal Phase A capacity is `entry quantity × primary ammunition per unit`; the mutable pool begins at that capacity and each firing unit consumes one shot. Two same-unit waves cannot lend or combine shots. Every slot occupied by a wave therefore reports the same `ammo_pool_shots`, `ammo_capacity_shots`, and derived `munition_percent = 100 × pool / normal entry capacity`. This is an explicit Phase A model/derived UI contract, not an independently verified reproduction of Ikariam's tooltip formula. Capacity is frozen when the entry batch is created, and later casualties do not shrink its denominator. Initial-garrison rejoin is excluded and may eventually require a richer replenishment ledger rather than changing this normal denominator silently.

A final partial volley uses named `EXP-AMMO-PARTIAL-ORDER-001`; native ranged selection remains primary, and an exhausted primary does not silently switch weapon. When multiple same-unit ranged waves occupy one runtime line, each wave fires as a separate volley from its own `ammo_pool_shots`; placement compaction never merges, transfers, or normalizes ammunition between waves.

Targeting uses the executable Art of Warfare priority table above; the former experimental legacy-targeting assumption is no longer active. Target priority is a property of the runtime line, not the unit type: a Swordsman in runtime flank uses `targeting.priorities["flank"]` (flank before long-range), while a Swordsman deployed in runtime first uses `targeting.priorities["first"]`. Individual shots re-evaluate the current highest-priority surviving formation, so target transfer after a formation is destroyed is executable rather than an unknown blocker. Active-weapon selection remains a separate step.

Accuracy is stored per weapon, including different secondary accuracy. No complete official algorithm is known: strict emits `UNKNOWN-ACCURACY`. Experimental uses `EXP-ACCURACY-CONCENTRATION-001`, a deterministic calibration hypothesis rather than Bernoulli hit/miss. If one hit can kill a full-health target it is applied without an Accuracy miss. Otherwise, inside the already-addressed target slot, damage spreads to the healthiest survivor while the most-damaged survivor's remaining HP% is above weapon Accuracy; once remaining HP% is <= Accuracy, subsequent hits focus the most-damaged survivor. This model changes only individual selection inside a slot and does not alter AM slot addressing, target-class priority, damage amount, ammunition, or firing chronology.

Support effects are distinct: Doctor/Tender are `healing`, Cook is `morale`. They appear in `deployed_support`, not ordinary reserve or Am slots. Strict retains `UNKNOWN-HEALING-ALLOCATION` and `UNKNOWN-MORALE-SUPPORT`. Experimental morale still uses `EXP-MORALE-NONE-001`; Doctor healing now executes only the order-invariant full-clear subset and uses `EXP-HEAL-NONE-001` only when total capacity is insufficient and partial allocation would matter. Doctor presence or arrival by itself does not emit the assumption. Arrival diagnostics aggregate repeated state waves of the same unit type within one entry batch, so `entry_batch_arrived.details.units` reports total quantity by `unit_id`. Before an engagement has actually started, pending arrivals whose native line can sustain/fallback the battle suppress an otherwise premature Round-0 winner and produce `waiting_for_arrival` events until the arrival round is reached. When both sides are empty at Round 0 but both have qualifying pending forces, the deployment-state event is a combined wait (`side=null`) with both `pending_sides`, per-side pending rows, and the earliest next arrival round. Future non-sustaining formations such as artillery alone do not delay a Round-0 defeat. This waiting rule is pre-engagement only; after both sides have reached a sustaining engagement, the existing round-boundary termination semantics continue to apply. Support never enters Am.

Current land units expose `unit_class = human|machine`. Machine land units are Steam Giant, Battering Ram, Catapult, Mortar, Gyrocopter, and Bombardier; the other current land units are Human. Doctor eligibility is constrained to Human combat units. The empirical paper supports a per-round healing effect that is already reflected before the next round's combat and explicitly uses Steam Giant as non-healable; current profile capacity is derived as 200 legacy HP × the v17 ×20 multiplier = 4000 per Doctor. Exact Healing/RR order and partial-capacity allocation remain unresolved, so the engine applies healing only when total capacity can clear all eligible persistent damage, an order-invariant result. Round result snapshots are post-combat but precede the next round's Healing/RR boundary: new same-round persistent damage therefore remains on deployed slots until the next round starts. `reserve_hit_points_percent` reports only damage currently assigned to Reserve by the most recent RR. If the supported Doctor full-clear subset removes all eligible Human persistent damage at that boundary, RR has nothing left to spread and Reserve may correctly remain at 100%.

Naval forum corroboration is field-specific: HP, armor, size, damage, shown secondary damage, and explicitly finite munition counts may cite *Workshop Tests: Ship Technology*. Accuracy cites only the current community reference because the forum accuracy fields are blank. Omitted munition does not prove infinity.

Experimental `naval-max` execution is now available. The max-field capacity evidence is the 2026 Gameforge-hosted community tutorial: First = 35 Steam Rams / 84 Fire Ships across 7 slots, Flank = 36 Ram Ships across 6, Long range = 42 Mortar / 56 Catapult / 84 Ballista across 7, First Strike = 25 Diving Boats / 15 Rocket Ships across 5, and Carrier/Carrier Evasion = 6 / 30 across 2 slots. The official in-game Help supplied by the user establishes the naval formation contracts: Support remains in Reserve and still applies; Carrier uses weakest-first and targets First Strike → Long-range → Front → Flank; First Strike uses strongest-first and targets Front → Flank; Long-range uses strongest-first and targets Front → Flank → Long-range; Front uses Heavy first, then Light, then out-of-ammo Long-range, with weakest-first and target priority Front → Long-range → First Strike → Flank; Flank uses strongest-first and targets Flank → Long-range → First Strike → Front; Carrier Evasion uses strongest-first and targets Carrier → Carrier Evasion. Formation fill order is Carrier → Carrier Evasion → First Strike → Long-range → Front → Flank; firing order is Carrier Evasion → Carrier → First Strike → Flank → Long-range → Front, with identical formations firing simultaneously. These target/fill/fire contracts are therefore no longer Experimental assumptions.

Tender current repair capacity is 4000 per Tender per round. The engine now executes the same order-invariant full-clear subset used for Doctor: if Tender capacity covers all naval persistent damage, it clears it before the next combat; if capacity is insufficient, exact allocation and Healing-vs-RR order remain unresolved and Experimental uses `EXP-TENDER-HEAL-NONE-001` rather than inventing a split. The official out-of-ammo Long-range → Front rule now reuses the same whole-wave round-start fallback architecture as land: when primary ammunition reaches zero and open Front slots can contain the whole surviving wave, the wave moves to Front, keeps its persistent damage wave-owned, RR redistributes after the move, and the ship uses its existing secondary/hull weapon. A case that would require one state wave to occupy Long-range and Front simultaneously remains under the general UNKNOWN-MULTILINE-WAVE-COMBAT-SEMANTICS guard rather than a naval-specific unknown. General D/P/M/IR/SR kill/redistribution selectors remain calibration work. Smaller naval battlefield geometries remain unsupported until independently verified. Barbarian fleets are confirmed game content, but the current repository does not fabricate a simulation-ready barbarian naval numeric catalog without a trustworthy current unit table.

## Other experimental policies and remaining unknowns

Current named Experimental policies include `EXP-D-KILL-SEQUENTIAL-001` (sequential D-kill/overkill-discard applied to the individual selected by the active targeting/Accuracy policy), `EXP-SWORDSMAN-FLANK-IKILL-EXACT-DIVISION-001` (historical Swordsman exact-division subset), `EXP-SWORDSMAN-SYMMETRIC-2HIT-ROW-PM-MKILL-001` (current full-formation row/P-kill M-kill hypothesis), `EXP-SLOT-DAMAGE-EVEN-001`, `EXP-ACCURACY-CONCENTRATION-001`, `EXP-IR-DISABLED-001`, `EXP-SR-DISABLED-001`, floor rounding, RR deployed-total rounding, ammo stop/partial ordering, `EXP-MORALE-NONE-001`, and conditional `EXP-HEAL-NONE-001`. The Swordsman selector is driven by reduced-Am structure rather than a fixed casualty lookup. All-even source columns stay D-kill. Exact aggregate division may use the historical I-kill subset. The modern M-kill candidate is deliberately narrower: only the full 6×40 central shape with six 7-hit source columns and a symmetric two-hit D-kill regime in both directions is modeled. It begins with the generic sequential D-kill result, retains one lethal-pair overkill per AM row (seven retained chunks), and converts that M-pool plus generic persistent damage into additional deaths and residual damage. This reproduces the current observed central results from the actual computed hit damage: 258 → 24 deaths + 12 damage; 183 → 21 deaths + 42 damage. The two 36-hit outer slots remain D-kill. Accuracy remains a candidate selector dimension, not a numeric multiplier, because the empirical paper explicitly leaves its IR/D-kill-column role unresolved. Responses and events expose only assumptions actually reached. A newer user battle report dated 2026-10-02 is intentionally a negative selector oracle: under the current Forge-5 working assumption the duel is approximately 259 damage in one direction (2-hit backbone) and 172 in the other (3-hit backbone), with observed 19/24 central-vs-outer casualties and 94% life on one side versus 12/14 and 98% on the other. ## Battle-end semantics

The versioned legacy/community battle-end profile separates `main_line_classes` (`first`), `fallback_candidate_classes` (`flank`, `second`), and definitely `non_sustaining_classes` (artillery, bomber, anti-air, support). Snapshots expose main-line and fallback counts plus `sustaining`, `fallback_required`, or `not_sustaining`. After the ordered formation phases for a round are resolved, a definite one-sided main-line loss terminates in that same round and leaves non-sustaining survivors out of casualties. Fallback-required states stop inconclusive. If both sides are definitely not sustaining, `UNKNOWN-BOTH-SIDES-NO-MAIN-LINE-OUTCOME` replaces the former unqualified draw. Initial definite termination timing uses `EXP-BATTLE-END-ROUND-BOUNDARY-001`; strict reports `UNKNOWN-INITIAL-BATTLE-END-TIMING`.

Battle-end evidence remains `CALIBRATION_REQUIRED`. The packaged profile records reviewer-verified community formation evidence and two Gameforge forum player battle-report evidence classes; these are not official specifications. The review did not supply their URLs and this environment could not retrieve them, so the records preserve titles, evidence class, verification actor, and an explicit missing-URL status rather than inventing links.

Experimental results list only assumptions actually reached. Partial-ammunition assumptions are conditional, assumption IDs are unique, and formation fallback is an unsupported boundary rather than an assumption that permits continued combat.

`BattleReportFixture` retains game version, complete scenario, round, casualties, damage%, and life%; damage display percentages can be converted to integer intervals rather than hard-coding a winner.

Scope is unit-vs-unit Phase A. Executable geometry, shared mixed-source Attacking Matrix support, and the narrow whole-wave Light→First fallback do not relax the remaining multi-line-wave, unsupported different-unit cross-wave rebuild, partial/ranged fallback, ranged-weapon, or secondary-trigger guards. Same-unit same-line replacement across waves is an explicit supported exception and preserves per-wave state. Town Wall input/stat metadata and configured Player/Barbarian over-limit initial open-field selection are implemented. Wall target priority and penetration eligibility are represented, but wall section shot allocation, wall Accuracy interaction, executable segment breaching, defender refill, flank-lock release, and calibrated execution of garrison-driven mid-battle geometry transitions are not implemented; the threshold itself is observable and guarded.

## Ranged formation calibration

The packaged calibration fixture is `USER_PROVIDED_BATTLE_OBSERVATION`, not Gameforge proof. Case A observes many surviving units in one ranged entry batch, but no supported exact surviving count: two pooled shots remain, the associated firing-eligible subset in the ranged line is two, additional same-batch units exist, and some non-firing remainder for that volley/formation appears at the front under conditions not yet generalized. Case B observes 838 alive and 282 shots: seven ranged slots are full and the non-firing remainder stays reserve/off-field instead of automatically filling an empty front. These cases establish that one wave may eventually occupy multiple runtime lines and that “no ammo → front” is invalid; they do not assign ammunition ownership to individual soldiers or enable fallback.

`Wave.slots` is structurally capable of storing distinct `line` values while ammunition remains on the parent wave, but the combat pipeline is not calibrated or safe for multi-line wave execution. In particular RR currently keys allocations by `damage_position`, which can collide across lines. `UNKNOWN-MULTILINE-WAVE-COMBAT-SEMANTICS` guards rebuild, RR, targeting, and firing. Unit metadata separates `semantic_class`, `native_line`, runtime slot `line`, and legacy `battlefield_class`. Deployment uses semantic/native formation rules, targeting uses runtime lines, and battle-end holding uses runtime first-line occupancy; `battlefield_class` remains serialized compatibility metadata and legacy profile vocabulary. Spearman remains semantic `light_infantry` with native/legacy line `first`.

`UNKNOWN-FORMATION-FALLBACK` is now narrower. The formation profile already establishes Heavy-before-Light and First-before-Flank. At round start, when a native Light Infantry wave can move **entirely** from its native line into currently open First slots, the engine executes that transition and preserves the wave's aggregate persistent damage for the normal RR pass; no stale-line round is fired. Cases that require splitting one wave simultaneously across First and Flank remain guarded by `UNKNOWN-MULTILINE-WAVE-COMBAT-SEMANTICS`. Long-range fallback remains guarded because its front-line weapon/secondary-trigger behavior is not established. The public `UNKNOWN-FORMATION-FALLBACK` boundary therefore remains for partial/multi-line Light fallback, Long-range fallback, and other placement/priority/damage-transfer cases outside this whole-wave subset.

## Initial-garrison defender privilege (documented unsupported)

`USER_PROVIDED_BATTLE_OBSERVATION` reports a privilege only for units owned by the battle-town owner, already stationed there at battle start, and belonging to the battle-start initial garrison. They may partially retreat into the city, rejoin after a later round, and refill ammunition; retreating a subset reportedly does not proportionally subtract the on-field pool. Allied defenders, attackers, and town-owner batches arriving after battle start instead retreat as a whole batch.

This behavior is **not implemented**. Future provenance and orchestration work is tracked as `UNKNOWN-INITIAL-GARRISON-PARTIAL-RETREAT`, `UNKNOWN-INITIAL-GARRISON-JOIN-BATTLE-AMMO-REFILL`, `UNKNOWN-BATTLE-START-PROVENANCE-PRIVILEGE`, and `UNKNOWN-LATE-JOINING-OWNER-RETREAT-RULE`. Multi-owner continuation is also `UNKNOWN-MULTI-OWNER-BATTLE-CONTINUATION`: current continuation is side-level with one logical owner per side, not a precedent for ejecting one owner independently.

## UI battle-state semantics

Player mode defaults to an upper attacker/lower defender field, matching the user-supplied in-game battle-report layout, with visual line slots, reserves, result and unsupported-boundary warnings, and round navigation. Air defense and bomber slots are rendered as a compact lateral air zone beside the central ground field, and flank slots are split to the left/right sides of the three central ground lines instead of consuming full-width rows. The simulator-only deployment snapshot remains accessible as a `部署` pager state rather than being presented as battle round 0. Browser setup defaults to the supported `land-max` battlefield and Forge level 5 on both sides; the initial Hoplite quantity is derived from the selected default field and fills its entire first line so a user can add Light Infantry and observe native flank placement without the default front being underfilled. When a user explicitly selects a battlefield with no flank geometry, the UI keeps any non-front Light Infantry in Reserve and shows a no-flank reserve note rather than making that placement look accidental. Hover/focus tooltips show registry display name, input upgrades, slot HP, and wave munition when applicable. Research mode adds batch IDs, native/current lines, reserve/ammo state, continuation state, events, and assumptions; it does not replace the player view.

`hit_points_percent` is engine-derived slot state using the current persistent-damage representation: `100 × (surviving count × unit HP − persistent slot damage) / (surviving count × unit HP)`. Dead units are absent from both numerator and denominator, matching the user-observed denominator rule. It is not claimed as a fully verified reconstruction of Ikariam's internal HP distribution while kill selection, damage distribution, and RR remain partly experimental. `munition_percent` is wave-level using the Phase A derived entry-batch contract above, so every slot of that wave shares it. Both are additive API fields; existing snapshot fields remain unchanged.

## Executable battle-report calibration

`evaluate_fixture()` compares a `BattleReportFixture` with a controlled simulator result, while `run_fixture()` keeps simulation and evaluation as separate steps. The requested round and slot are addressed by side, runtime line, and damage position; physical position is never calibration identity. Every requested field produces its own deterministic `match`, `mismatch`, or `not_assessable` assessment, and result metadata preserves simulator status, reached round, and named unsupported blockers.

Damage-percent observations use the existing documented round-up assumption to derive the exact compatible integer persistent-damage interval from surviving units × unit HP. This remains a calibration assumption rather than confirmed Ikariam law. Casualties are summed only from round `damage` events carrying exact target side, runtime line, and damage position; missing identity is not inferred from side totals. Battle-report `life_percent` remains `not_assessable` with `UNKNOWN-BATTLE-REPORT-LIFE-PERCENT-SEMANTICS`, because the report denominator and rounding have not been proven identical to engine-derived `hit_points_percent`.

A calibration match says only that one simulator result is compatible with one observation. The current Swordsman fixture validates both casualties and the integer life display under the row/P-kill hypothesis without hard-coding the observed casualty vector: strong-source central slots end with 12 aggregate damage on 16 survivors and weak-source central slots with 42 on 19 survivors; both are below 1% damage and therefore display as 99% life under the empirical rule that life percentage is rounded down. Mixed-source Am row/column construction is now an executable empirical-paper contract; the official Accuracy algorithm remains unknown while Experimental uses the named concentration hypothesis. RR slot-internal allocation, SR/IR trigger, secondary-trigger, ranged-fallback, unsupported cross-wave rebuild, and multi-line-wave blockers remain intact. Formation firing order and class-level shot-by-shot target transfer are executable current contracts.


## Military economy and General Score

The `military-economy-current` profile is presentation/reporting data, not a combat modifier. The current community score rule states that active military units and ships contribute 0.02 General Score per unmodified production resource, equivalent to one General point per 50 resources; reduction buildings do not reduce the score basis. The current land-unit GEN values are cross-checked against that formula, and the profile loader rejects any row whose published score does not equal `resource_cost_basis_total / 50`.

Spartan is a special case: its stored 40 + 40 resource values are nominal score-basis values rather than resources actually paid for recruitment, so its 1.6 score remains valid without pretending that 80 resources were spent. Population is not part of the General Score formula. Workshop levels, Forge/Hephaistos, and combat buffs are deliberately absent from the economy calculation.

Battle output derives `general_score_lost` only from actual casualties and derives `general_score_destroyed` as the opposing side's loss. `gross_damage_dealt` is separately the sum of simulator `damage` events; it is an engine observability metric and is not claimed to be an independently verified Ikariam war-report field with identical semantics.
